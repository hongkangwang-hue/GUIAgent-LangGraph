# GUIAgent-LangGraph 阶段性结果汇报

> 截至 2026-10-06。项目停止新增实机实验，以现有证据作阶段性汇报。
> 本文中的客机批次数字来自操作者提供的控制台输出；相应原始 JSON 未同步到主机复核。

## 可直接口头汇报的版本

本项目实现了桌面截图感知、任务拆解、键鼠执行、程序化终态判定、轨迹记录和安全急停，并接入 LangGraph 编排。使用阿里云百炼 `qwen3-vl-8b-instruct`、`planner_v8` 与 `executor_v5` 时，客机一次统一的五项基础任务、每项五轮测试，控制台报告 25/25 通过；首步成功 19/25，人工干预 0/25，安全事件 0。该批原始存档尚未同步复核，也没有在同一 VMware 快照下完成 legacy 与 LangGraph 的严格对照，因此不能把结果解释为跨环境稳定性或 LangGraph 相对 legacy 的提升。

第七周定义了 20 项桌面任务，但探索试跑多次提前中止。已记录的一次较完整试跑只启动了 14 项，其中 9 项通过，后续 6 项未执行；这不是 20 项成功率，也不是正式重复评测。失败或中止暴露出窗口残留、焦点与导航、重复无变化点击、Copilot 误触、接口配额错误等问题。项目随后增加起点重置检查、连续无变化点击限制、终态检查和安全哨兵，但改进后的 20 项完整批次仍未完成。

最后一次 `qwen3.7-plus` 单项试验针对“新建文件夹”：文件存在判定通过，15 步、49.3 秒，但模型没有自报完成，连续第三次发送回车触发 `sentinel:repeated_input` 急停，安全事件 1。因此只能表述为**一次在急停后仍满足目标文件判据的单项结果**，不能表述为稳定成功，也不能与先前的 `qwen3-vl-8b-instruct` 批次直接比较。由于时间限制，本项目以完成原型、基础任务批次和部分探索性评估作为阶段性成果；完整 20 任务评估、同快照引擎 A/B、鲁棒性实测与演示视频均未完成。

## 五项基础任务的主要问题与修改经过

### 共通调整：把每轮起点和结果判定做实

早期批测发现：只清理文件或结束应用进程，不能清掉记事本的会话恢复、开始菜单浮层、登录框和上一轮窗口。下一轮模型看到的桌面因此不同，甚至出现没有做动作却满足成功判据的假成功。后来在各任务 reset 中加入 `tasks/reset_desktop.py` 清理浮层与窗口，并为成功判据设置反方向的 `precondition`：例如“打开浏览器”开跑前必须确认 Edge 尚未运行，“关闭应用”开跑前必须确认计算器已经运行。起点未建立的轮次标为无效，不计入成功率。记事本会话恢复在客机设置中关闭；任务栏取消固定曾引出登录框的 Copilot。相关记录见 `7335b93`、`60452c0`、`7bb86b1` 和旧版 `docs/m2-basic-tasks-report.md` §3。

完成判定逐步从模型自报的 `done` 转向进程、窗口或文件副作用；这使“模型认为完成”与“实际任务完成”可以分别记录。LangGraph 执行循环后来作为并存路径加入（`f2767ad`），本次 5×5 选择了 `--engine langgraph`。没有同快照、同模型、同提示词的 legacy/LangGraph A/B，不能把最终 25/25 归因于框架本身。

### 1. 打开浏览器 `open_browser`

**问题。** 早期统一批次中，这项已能达到 5/5，但平均约 6 步，说明打开一个应用仍有冗余动作。旧的测试起点若留着 Edge，单靠“进程在运行”会造成假成功。排查浏览器相关失败时还怀疑过桌面图标双击没有生效；客机定点验证的“直接双击”“先单击再双击”“先单击再回车”三条路径都能启动 Edge，因此不能把搜索失败归咎于双击执行器。

**调整。** 每轮先关闭旧 Edge 并清理桌面，再检查 `msedge.exe` 在开跑前不存在；成功时才检查进程出现。浏览器搜索曾误点邻近的 Copilot 图标，因此客机还取消了 Copilot 的任务栏固定项。双击诊断见 `840c18c`；最终的清场和起点判据在 `tasks/basic_tasks.yaml`。本项近期没有单独新增特殊执行路线。

**结果。** 最终 LangGraph 统一批次控制台为 5/5，平均 2.2 步、5.8 秒。与旧批的步数差异涉及环境、提示词和代码版本，不能只归功于某一个改动。

### 2. 搜索指定内容 `search_content`

**问题。** 旧判据只查标题包含“Python”，曾匹配到评测脚本自己的命令行窗口，把一次未搜索的任务误判为成功。另一次旧批次为 0/5：Edge 已打开，但规划器把“点击地址栏”拆成独立子任务；点击已聚焦的地址栏几乎不改变截图，模型便反复点击，耗尽步数而从未输入搜索词。其他试跑还出现过误点 Copilot，以及搜索框出现旧剪贴板内容的现象。

**调整。** 判定器排除自身控制台，标题条件收紧为 `Python.*Edge`（`9e750d9`）。规划器把“聚焦地址栏”和“输入 Python 官方文档”合并成有可见文字结果的目标（`67b64d5`）。执行器推迟恢复剪贴板，避免粘贴目标文本时旧内容抢先进入输入框（`c75b3f1`）；旧截图与这一机制相符，但不能仅凭截图证明它是唯一原因。客机也取消固定 Copilot，清理残留登录框。

**结果。** 修复后先有单轮 1/1；最终统一批次控制台为 5/5，平均 6.0 步、11.3 秒。

### 3. 打开指定文件 `open_file`

**问题。** 模型曾把完整路径输进记事本正文，或在“打开”对话框重复输入，使文件名错误。Windows 11 记事本会恢复旧标签页：旧版即使对话框未关闭，目标文件标题也可能已经在后台，从而产生判定误报。另一次轨迹显示模型在文件对话框同一坐标连续点击、画面无变化，始终没有输入路径。

**调整。** 客机关闭记事本会话恢复；任务起点检查目标文件存在且旧记事本进程退出。成功判据改为目标文件标题精确匹配、记事本进程存在，并要求“打开”对话框已经消失；判定器补查前台模态窗口（`fa3407d`、`45e45b3`、`63cf0ab`）。输入绝对路径前，执行器确认前台确是记事本的“打开”对话框，否则拒绝输入并反馈。`planner_v8` + `executor_v5` 引导文件名框已有焦点时直接输入完整路径；连续无变化点击会触发反馈与停止，最终 `done` 还要接受真实终态检查（`63cf0ab`）。

**结果。** v8 修复后单轮 1/1、13 步、33.2 秒；最终统一批次控制台为 5/5，平均 12.0 步、23.0 秒。旧版“5/5”中有过打开对话框仍在的可疑轮次，因此不能把旧数字作为可靠的修复前基线。

### 4. 发送消息 `send_message`

**问题。** 上一任务留下的记事本曾抢走焦点，模型把“你好世界”输错窗口。另一轮中，模型对未聚焦的消息输入框连续执行两次输入而画面不变，第三次重复输入被安全哨兵叫停。手动点击输入框后粘贴成功，说明该次问题集中在焦点与动作顺序。测试消息程序按回车就会发送，旧计划又要求随后点击发送按钮，可能重复提交；旧的“日志包含文字”判据仍会给重复消息打勾。

**调整。** 每轮清理旧窗口并重置本地消息程序与日志。规划器要求先点击输入框，再输入正文，只提交一次，并把“输入—发送”合并成以消息列表出现为终点的目标（`83ca9f0`、`9e0ddf6`）。成功判据改为 `messages.log` 中“你好世界”**恰好出现一次**，防止重复发送也算成功（`83ca9f0`）。这里的消息程序是本地模拟界面，不向真人发送。

**结果。** 修复后单轮 1/1、4 步、14.6 秒；最终统一批次控制台为 5/5，平均 4.2 步、10.4 秒。

### 5. 关闭应用 `close_app`

**问题。** 任务目标是关闭计算器，但早期 reset 若未成功启动计算器，“计算器进程不存在”的成功判据会在 Agent 动作前直接成立。另一方面，旧 reset 只启动新计算器，不结束前一轮残留进程，可能让每轮起点累积更多计算器。Windows 11 计算器是 UWP 应用，杀掉后冷启动有时超过固定 3 秒等待，使本应有效的轮次被错误标为起点无效。

**调整。** reset 改为先结束旧 `CalculatorApp.exe`，再启动计算器并轮询等待进程出现；开跑前必须确认进程正在运行。任务成功时检查进程退出，而不是只检查是否点过关闭按钮。相关提交为 `3247259`、`8a50e38`，起点判据见 `60452c0`。因此测试画面中“计算器先打开、随后自动关闭”正是这一任务的预期流程。

**结果。** 最终统一批次控制台为 5/5，平均 2.0 步、4.5 秒。该项主要修的是评测起点与判定可靠性，近期没有记录到专项的新模型动作修复。

以上旧批次的 0/5、4/4 或 5/5 分别来自不同日期、环境、版本与判据；它们帮助定位问题，但不能直接作为严格单变量“修复前后提升”。最终五项 25/25 仍以本报告前述统一批次的控制台口径为准，原始 JSON 尚待主机复核。
