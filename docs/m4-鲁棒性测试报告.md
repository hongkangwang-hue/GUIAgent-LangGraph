# 系统鲁棒性测试报告

> 大纲第 6 周交付物。数据来自 405 步真实客机执行轨迹，所有数字可从
> `docs/m2-runs/` 与 `outputs/trajectories/` 的原始记录复算。
> 完成日期 2026-09-22。

---

## 一、这份报告测的是什么

第 6 周的核心工作是"高级功能与系统鲁棒性优化"。鲁棒性不是一个可以直接
测量的量，所以本报告把它拆成三个能回答的问题：

1. **系统会以什么方式失败？** —— 错误分类，基于 405 步真实数据
2. **加进去的容错机制到底管不管用？** —— 重试升级、Reflector、安全哨兵三项的实测
3. **失败之后能不能恢复？** —— 恢复率，按错误类型分项

需要先说明一个口径问题：**本项目通篇不设硬性成功率门槛。** M4 的 11 条验收
标准里没有一条要求端到端成功率达到某个数值。它要求的是"做出东西、量出数字、
说清来源"。因此本报告不以成功率高低论成败，而以"失败形态是否被准确刻画、
机制是否有实测依据"为标准。

## 三、系统怎么失败的：错误分类

对 405 步逐步打标，得到四类失败形态。分类不是事先设计的，而是从数据里归纳
出来的——这一点很重要，先设计分类再往里套，套不进去的失败就会被忽略。

### A 类：走错路（占比 94.4%）

动作执行了、屏幕也变了，但方向不对。最典型的证据是**"做完了"这个判断完全
失效**：

```
90 个以 done 收尾的子任务中
  执行 0 个动作就报完成    12   13.3%
  执行 1 个动作就报完成    73   81.1%   ← 主峰
  执行 2 个              3    3.3%
  执行 3 个以上           2    2.2%
```

**94.4% 的子任务在做了 0~1 个动作之后就宣布完成。** 1024×768 那轮更极端：
25 轮全部以模型自报完成收尾，程序化判定 0/25。

这说明"靠模型说 done 来退出"在这个规模的模型上**等于没有退出条件**，
真正在兜底的是步数上限。

### B 类：点空了（占比 38.0%）

动作执行状态是 `ok`，但屏幕纹丝不动。开了帧差检测的那 220 步里：

```
动作执行后屏幕变了   49 次
动作执行后屏幕没变   30 次   ← 38.0%
```

这一类特别危险，因为**它和成功的点击在日志里长得一模一样**。执行器只能
保证"鼠标事件发出去了"，保证不了"点中了目标"。典型案例是 `close_app`：
点击返回 `ok`，计算器进程仍在。

### C 类：执行层错误（占比 0.5%）

185 步里只有 1 步。把动作执行成功率单独算出来：

```
动作执行成功率 = 94 / (94 + 1) = 98.9%
```

（另有 90 步是 `no_action`，即模型报 done 没有动作可执行，不进分母。）

**执行层几乎不出错。** 这个数字和 B 类的 38% 放在一起看才有意义：执行器
可靠，瓶颈在上游的模型定位。

### D 类：坐标塌向屏幕中心

客机上 51 次带坐标的动作里，x 中位数 508（模型空间 0~1000），**54.9% 落在
[480, 540] 这个窄带里**，映射到 1920 宽的屏幕约等于水平中线。而在训练同
尺寸的 1024×768 图上，预测坐标铺得很开（82.2% 不重复）。塌陷只发生在客机上。

推测与宽高比有关（训练 4:3，客机 16:9），但**未做验证实验**，样本量也只有
51 次，不足以支撑精确结论。

## 四、三项容错机制的实测

### 4.1 重试升级：不是"多试几次"，是"换一种做法"

触发这项工作的是一条具体轨迹：

```
子任务「点击任务栏上的 Microsoft Edge 图标」
   left_click (15, 190) × 6      execution_status 全部 ok
```

六次点击全部"执行成功"，什么都没发生。而轨迹探针量到，离线组的**动作重复率
是 75.3%**——一半以上有重试的子任务里，每一次尝试完全相同。

**所以"把步数上限从 6 调到 12"是无效的，只是把同一个错误做十二遍。**

实现的是升级而非重复：同一位置单击无效就改成双击。触发条件要求
"重复"且"屏幕未变"两条同时满足。支撑证据：

| | 轮次 | 成功 |
|---|---:|---:|
| 出现过 `double_click` 的 | 2 | **2** |
| 全程只有 `left_click` 的 | 8 | **0** |

Fisher 精确检验 p = 0.0222。

升级阶梯**只有一级**（`left_click → double_click`）。更长的阶梯需要证据，
而目前只有这一条有实测。没有证据的阶梯不写——它们会让失败原因更难查。

### 4.2 Reflector：触发率达标，纠错能力为零

Reflector 用帧差等三级级联判断模型自报的 `done` 可不可信。220 步里判定 138 次：

```
accept    74   53.6%
reject    57   41.3%
unknown    7    5.1%
```

**级联 1（帧差）单独得出了 94.9% 的结论**，语义判定级联触发率 0%，远低于
验收标准要求的"≤30%"。设计假设"绝大多数步骤应在前两级出结论"成立。

同快照对照（仅差 Reflector 开关）：

| | 无 Reflector | 有 Reflector |
|---|---:|---:|
| 程序化判定通过 | 5/25 = 20% | **10/25 = 40%** |
| 模型自报完成 | 25/25 | 22/25 |
| 自报完成但判定未通过 | 20 | **12** |

看起来是 2 倍提升。**但这个结论必须打折**，理由在下一节。

### 4.3 安全哨兵与急停

项目中出现过三次真实安全事件：Agent 修改并保存了 `.env` 文件；对着真实微软
账号的身份验证界面连按 12 次回车；进入 Edge 的数据导入对话框，且"保存的密码"
处于勾选状态。

三次事件有一个共同点：**每个动作单独看都完全合法**。原有的安全护栏只检查
动作本身（输入文本像不像危险命令、组合键在不在黑名单），看不到动作发往哪个
窗口。而三次都发生在无人值守的批量跑里，热键急停要有人按才有用。

因此新增哨兵机制：动作执行前检查前台窗口与重复输入，命中即触发急停、整批
停下等人处理。急停热键客机实测响应延迟 **271 ms**，`wait` 动作被切成 50 ms
轮询以保证急停在等待期间仍然有效。

能力边界如实声明三条：**拦不住第一下**（前台窗口是动作执行前的状态）；
**标题匹配会误报也会漏报**（偏向误报，误报代价是停一批让人看一眼）；
**拦得住"犯傻"，拦不住"规避"**。真正的安全边界仍然是隔离虚拟机。

## 五、一次撤回：恢复率从 90% 修正为 0%

本报告最值得记录的不是某个机制有效，而是一次统计错误的发现过程。

初稿报告 Reflector 的错误恢复率为 **90.0%**。复核时拆开这 30 次否决的后续：

```
真正恢复       0    0.0%
到上限强制接受  27   90.0%
```

初稿把"到上限强制接受"算成了恢复。**真实恢复率是 0/30 = 0.0%，虚高整整
90 个百分点。**

根因是把两件事混为一谈：**安全阀触发说明系统没有崩溃，不说明问题被解决了。**
Reflector 连续否决到上限后会强制接受，这是防死循环的设计，不是恢复。

同样的审慎也适用于 4.2 节那个"2 倍提升"。按任务拆开看，两个改善的任务
（`close_app`、`send_message`）**恰好也是耗时增加最多的两个**：

```
close_app      18.3s → 26.1s   +7.8s    0/5 → 2/5
send_message   49.8s → 64.9s  +15.1s    0/5 → 3/5
```

而程序化判定在循环结束之后才跑。本项目已记录过计时敏感的直接证据：UWP
计算器冷启动超过 3 秒导致起点未建立。`close_app` 正是那个已知受异步时序
影响的任务。**所以那 2 倍里有多少来自 Reflector、多少来自"多等了几秒"，
现有数据分不开。**

结论：Reflector 保留，但**默认关闭**（`--reflector` 开关）。一个纠错能力
实测为零的模块不应默认开启。

## 六、v1.0 → v2.0 的变化

| 项 | v1.0 | v2.0 | 默认 |
|---|---|---|---|
| 重试策略 | 无 | 同位置无效则升级动作类型 | 关 |
| `done` 判据 | 只信模型 | 帧差三级级联（Reflector） | 关 |
| 安全检查 | 只看动作本身 | 增加前台窗口与重复输入检查 | 开 |
| 动作后等待 | 固定 0.8 秒 | 自适应，连拍到界面稳定 | 关 |
| 评测指标 | 成功率、步数、耗时、成本 | 增加首步成功率、人工干预率、安全事件数 | 开 |

**四项新机制中有三项默认关闭**，这是刻意的：它们都会改变模型看到的内容或
系统的行为，而 M2~M5 的全部端到端数字都是在关闭状态下跑出来的。默认打开
会让新旧数据失去可比性，而这条对照链是本项目最有价值的资产。收益用 A/B
对照单独给出。

## 七、尚未完成的部分

如实列出，不以"已完成"含糊带过：

| 项 | 状态 | 原因 |
|---|---|---|
| 3 个长任务的实测数据 | 任务集与环境脚本已就绪，**未跑** | 需要客机一轮，约 2 小时 |
| 自适应等待的 A/B 收益 | 代码与统计函数已就绪，**未跑** | 同上 |
| 新增三项指标的实测值 | 代码已就绪，**无数据** | 现有轨迹跑在这些指标实现之前 |
| 回滚动作 | **未实现** | 交付物 3 要求的另一半 |
| 连续运行 1 小时稳定性 | **未测** | 现有旁证：单轮 30~50 分钟未崩溃 |

还有两条验收标准的**口径需要修正**，不是没做而是不适用：

- **标准 7（OCR 调用次数减少 40%）**：OCR 与元素检测模块共 2371 行，但
  **主循环从未调用过它们**。模式 A 下模型直接输出坐标，不需要感知模块参与。
  基线为 0，"减少 40%"无从谈起。
- **标准 9（API 成本下降）**：离线本地推理的 API 成本恒为 0 元。

两条都建议在验收时改口径，并说明理由，而不是制造一个形式上达标的数字。

## 八、结论

1. **系统的失败以"走错路"为主（94.4%），不是"操作失败"。** 执行层动作成功率
   98.9%，瓶颈全在上游的决策与定位。
2. **"模型自报完成"这个退出条件是失效的。** 94.4% 的子任务在 0~1 个动作后
   就报完成，干净基线上 25 轮全部如此而实际成功 0 次。真正在兜底的是步数上限。
3. **重试要有效，前提是每次尝试真的不一样。** 动作重复率 75.3% 证明单纯增加
   步数预算没有意义；"单击升级为双击"有 p=0.0222 的实测支撑。
4. **Reflector 的触发率设计成立，但纠错能力实测为零。** 表面 2 倍的端到端
   提升与耗时增加高度共线，现有数据无法归因，因此默认关闭。
5. **安全机制的能力边界必须写明。** 哨兵拦得住模型犯傻，拦不住有意规避；
   真正的边界是隔离虚拟机。

下一步的优先级：先补齐长任务与自适应等待这两轮实测（各约 1 小时），
再做回滚动作；标准 7/9 的口径问题在验收时说明。
