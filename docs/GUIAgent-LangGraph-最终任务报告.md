## 一、项目目标与完成概况

项目目标是在 Windows 桌面上实现一个接受自然语言指令、观察屏幕、拆解任务、执行键鼠动作并核查结果的 GUI 智能体。执行在 VMware 客机内，在线规划调用阿里云百炼视觉模型；系统也提供本地模型接入路径。主体模块包括屏幕捕获、DPI 与坐标换算、OCR/UIA 识别、动作执行、任务规划、Agent Loop、LangGraph 执行路径、程序化判定、轨迹记录和安全急停。

本项目形成了环境与系统设计文档、桌面感知与控制模块、Agent 框架、端到端原型、本地模型微调、鲁棒性机制、20 项任务定义及阶段性实测材料。本报告按周汇总交付内容，并以实际运行记录说明评测结果。

## 二、系统实现与评测方法

系统运行链路为：

```text
自然语言指令 → Planner 拆分子任务 → 客机截图 → 模型给出结构化动作
             → 坐标换算与安全检查 → 客机键鼠执行 → 截图/轨迹反馈
             → 程序化终态判定
```

`agent/session.py` 编排会话，`agent/planner.py` 负责拆解；`perception/` 负责截图、DPI、坐标与可选的 OCR/UIA；`control/` 执行动作并检查安全约束；`core/loop.py` 和 `core/graph_loop.py` 分别提供 legacy 与 LangGraph 执行路径；`core/verify.py` 用进程、窗口和文件判据核查任务；`core/trajectory.py` 逐步记录轨迹。CLI 的 `run` 默认演练，只有显式 `--execute` 才发送真实键鼠事件。[第 4 周交付说明](../delivery/W4-端到端GUI智能体系统v1.0/README.md)记录了原型结构。

评测遵守三条口径。第一，模型的 `done` 只记录自我判断，**成功由程序化判据决定**。第二，每轮先 reset，再检查起点是否处于目标的反方向；起点无效的轮次不计成功率。第三，不同模型、提示词、提交、屏幕或快照的批次分开报告，不把单轮 1/1 写成稳定成功。

## 三、每周工作与交付证据

### W1：技术调研与开发环境

完成了 GUI 智能体、视觉语言模型、GUI grounding 等方向的相关工作梳理，并在[相关工作与系统设计](技术报告-相关工作与系统设计.md)中形成章节。搭建 Python 3.10、PyTorch/CUDA、截图、OCR、键鼠和测试环境，并编写自检脚本与安装说明。[第 1 周环境文档](第1周交付物-开发环境配置文档.md)记录自检必过项 **5/5**、229 个单元测试通过和 1 个跳过、当时 `perception` 与 `control` 的语句覆盖率 **77%**。这些是该周环境阶段的数字，不替代第 2 周交付包的测试口径。

### W2：桌面感知与控制模块

交付[桌面感知与控制模块](../delivery/W2-桌面感知与控制模块/README.md)：`dxcam`/`mss` 截图与降级、DPI 感知和坐标缩放、PaddleOCR/EasyOCR 与 UIA/OCR 融合、结构化鼠标键盘动作、中文剪贴板输入、截图标注和安全急停。客机验证过截图与动作链；OCR 双引擎和元素召回率另有独立报告。交付包[单元测试报告](../delivery/W2-桌面感知与控制模块/单元测试报告.md)给出 **216 个用例：215 通过、1 有意跳过、0 失败；语句覆盖率 76%**。

技术边界：这些模块具有跨平台接口，但项目主要在 Windows 11 上实测；OCR/UIA 有独立验证，后续模式 A 的主执行循环直接使用模型输出坐标，**未将 OCR 识别结果接入主决策链**。

### W3：公开 GUI 数据与基础 Agent 框架

交付[数据集处理与 Agent 框架](../delivery/W3-数据集处理与Agent框架/README.md)。预处理流水线完成装载、统一字段、清洗、统计和会话级冻结划分；[数据集统计](数据集统计分析报告.md)共 **6,555 条样本、3,973 张不重复截图**。实际完整处理的主要来源是 ScreenSpot、ScreenSpot-v2 和 ScreenAgent；Mind2Web 经分析未混入，WebArena 未作为完整训练集装载。这与最初列举的公开数据集组合有差异。

Agent 层实现任务拆解、上下文管理、YAML 提示词和模型调用抽象，支持在线 API 与本地服务接入。第 3 周交付时执行循环仍由项目自写，LangChain 主要用于模型调用；后来增加 `core/graph_loop.py` 的 LangGraph 编排路径。[第 3 周单元测试报告](../delivery/W3-数据集处理与Agent框架/单元测试报告.md)记录 **369 个用例全过、三个本周模块语句覆盖率 88%**。后期 LangGraph 五项基础任务批次按其独立测试条件报告，不将批次结果作为框架间的因果比较。

### W4：端到端原型与基础任务

交付[端到端原型 v1.0](../delivery/W4-端到端GUI智能体系统v1.0/README.md)：将屏幕感知、规划、动作执行、截图反馈、程序化判定及逐步轨迹串联；CLI 提供 `run`、`replay`、`label`、`config`。该周[原版基础任务报告](../delivery/W4-端到端GUI智能体系统v1.0/基础任务测试报告.md)汇总为 **19/24**：打开浏览器 5/5、打开文件 5/5、关闭应用 5/5、发送消息 4/4、搜索内容 0/5。消息任务排除了 1 轮人工碰鼠标的样本，主结果由全量批次与一次补跑组成；耗时不能跨这两个批次直接比较。交付包另有 **221 个测试全过、语句覆盖率 77%**。

本阶段发现环境残留会改变下一轮的屏幕输入：记事本会话恢复、开始菜单、Copilot 登录框和旧窗口都曾造成失败或假成功。后续加入清场、起点检查、严格终态判据、剪贴板时序修正和任务专用提示词。五项任务的问题与修复经过已在[阶段性结果汇报](20261006-阶段性结果汇报.md)逐项记录。

### W5：QLoRA 微调与效果对比

交付[第 5 周模型和报告](../delivery/W5-LoRA微调模型与效果对比/README.md)。这部分微调的是**本地 Qwen2.5-VL-3B-Instruct 执行器**：输入当前桌面截图与一个子任务，输出 JSON 格式的下一步 GUI 动作；它与后期通过阿里云百炼 API 调用的 `qwen3-vl-8b-instruct`、`qwen3.7-plus` 是不同模型，不能混作同一次实验。目标动作包括点击、双击、鼠标移动、输入文字、按键、滚动、等待和 `done`，鼠标坐标统一到 `[0,1000)`。

**数据准备。** 从 ScreenAgent 桌面轨迹提取单步动作，以完整会话而非相邻截图随机划分，得到 **1,783 条训练样本（165 个会话）和 375 条验证样本（38 个会话）**，会话交集为零。全部截图为 1024×768。第一版数据清洗错误地要求每条样本都带坐标，只留下 716 条鼠标动作，漏掉基础任务所需的 `type`、`key`、`done`；项目随后重建了八类动作数据，将指令由会话总目标改成当前子任务，并把按键名映射到执行器词表。重建同时改变了样本量、动作覆盖、指令粒度和语言，不能把版本差异归因于某一项。重建后全量 2,158 条中 `done` 占 **41.6%**，这一分布也是后续提前结束问题的重要线索。

**训练与纠错。** 使用 4-bit NF4 双重量化、bf16 计算和 PEFT/QLoRA；LoRA 配置为 `r=16`、`alpha=32`、dropout `0.05`，覆盖注意力投影和前馈投影；学习率 `1e-4`，2 个 epoch，批大小 1、梯度累积 8。可训练参数 **3,715 万 / 20.71 亿（1.79%）**。保存的训练记录给出 RTX 4090 24GB 上约 **93 分钟、峰值 7,458 MB**；原始完整训练日志已不可用，这组资源数字以保存记录为准。第一次训练的提示词只列出四种鼠标动作，却要学习大量键盘与 `done` 标签；同时 assistant 标签掩码偏移 3 个 token。修正提示词和掩码后，用相同数据与超参重新训练，并通过掩码断言、训练告警检查和非零 LoRA 权重确认训练路径。两次 loss 曲线相近，故没有用 loss 下降单独证明修复有效。交付的是适配器及配套报告，原始基座权重未放入公共主仓库。

**离线评估：微调后的单步动作生成确实改善。** [微调效果报告](../delivery/W5-LoRA微调模型与效果对比/微调效果对比分析报告.md)在同一 375 条验证集、同一提示词下比较基座与微调模型，得到下表结果。这里的“全量命中”要求动作类型及对应坐标或参数同时正确，比单看 JSON 能否解析更严格。

| 指标 | 微调前 | 微调后 | 说明 |
|---|---:|---:|---|
| JSON 格式合规率 | 24.0% | **100.0%** | 模型学会稳定输出可执行的结构化动作 |
| 动作类型准确率 | 15.5% | **59.7%** | 判断下一步应做哪类动作的能力明显提高 |
| 全量命中率 | 4.0% | **49.1%** | 动作及必要参数同时正确的比例提高 |
| 归一化坐标误差中位数 | 144.5 | **49.7** | 离线定位误差下降，但不能直接推出新桌面上的定位成功率 |
| `done` 误报率 | 7.8% | **36.5%** | 该项退化：尚需继续时过早报告完成更多 |

因此，“微调后的数据变好了”对**这组离线单步指标**是准确表述；同时应保留 `done` 误报率上升这一不利结果。另在 99 条坐标样本上比较过提示词，在 53 条严格配对样本上比较图像缩放：模拟部署时约 `0.622` 的缩放使坐标 50 单位内命中率 **53%→4%**，动作类型判断仍为 **47/53**。这说明该模型的定位对输入尺度敏感；验证集又来自训练数据的同一来源，尚不能代表客机 Windows 11 界面上的端到端效果。

**实机结果与边界。** 本地微调模型早期在 1920×1080 客机上曾记录 **5/25**，但五次均来自“打开浏览器”，轨迹提示可能点击了同样会启动 Edge 的 Windows 聚焦图标；该批与后续测试的快照和分辨率也不同，不能作为严格的微调前后对照。随后在 1024×768 的受控客机快照上，微调模型执行五项基础任务各五次，程序化通过 **0/25**；25 轮均由模型自报完成，86 个子任务中有 19 个在没有成功动作时就报告 `done`。这说明那一批**端到端任务未通过**，不推翻离线单步指标的明确提升；训练与客机同为 1024×768 仍为 0/25，也说明分辨率失配不能单独解释失败。离线验证使用 bf16，客机本地服务默认 4-bit；新版验证集的对应 4-bit 指标未测，也没有同配置基座模型的客机 A/B。第 6 周又在另一环境中使用同一微调模型比较容错机制，出现 5/25→10/25；这比较的是机制开关，不能算作再次微调带来的收益。后期百炼 API 的 25/25 使用另一模型，也不能归为本地微调成果。

### W6：鲁棒性与安全

交付[鲁棒性测试报告](m4-鲁棒性测试报告.md)和相关机制：无变化动作的重试升级、Reflector 的分层检查、自适应等待、前台窗口与重复输入安全哨兵、实时面板和逐步轨迹。报告基于**同一微调后本地 3B 模型**的两批共 **405 步**轨迹分析。一次同快照、仅切换 Reflector 的对照中，程序化通过数为 **5/25→10/25**；但改善与耗时增加共线，不能把差值完全归因于 Reflector，也不能解释为模型权重再次提升。报告曾把“达到否决上限后强制接受”误计为恢复，复核后纠正为**真正恢复 0/30**，因此 Reflector 默认关闭。

新增安全指标在后来的基础任务客机批次才得到控制台报告值，不应回填到 W6 旧轨迹。OCR 未进入模式 A 主循环，因此本报告不计算主循环 OCR 调用变化。

### W7：20 项任务集与探索性评估

已在 [`tasks/desktop_20.yaml`](../tasks/desktop_20.yaml) 定义 **20 项任务：单步 7、多步 10、复杂 3**，前五项沿用基础任务。第七周多次 20×1 探索批次提前中止；其中一批客机控制台报告 **14 项启动、9 项通过、5 项未通过，后 6 项仅在该批未运行**。第 10–13 项出现无效重复点击或模型自报完成而文件判据未通过；第 14 项误触 Copilot，引发安全急停。2026-10-07，第 15–20 项又分别完成首次单项实测，**1 项通过、5 项未通过**；它们不属于前述同批结果。因此截至本报告，20 项都已有至少一次实机尝试。[20 项逐项记录](20261006-20任务执行情况逐项汇总.md)列出每项目标、状态及原因判断边界。

原 20×1 探索批次运行至第 14 项急停，后 6 项**只是在该批未运行**；第 15–20 项后来均已完成至少一次单项实机尝试。后来的六次单项记录使用不同提交、未记录快照名，不计算 20 项统一批次成功率。既有分辨率与模型实验来自其他批次，按各自条件单独解释。

### 4.3 五项基础任务：问题与实际修复

**共通处理。** 早期每轮桌面状态不一致：记事本恢复旧标签、开始菜单或登录框遮挡、上一轮窗口残留，都会改变模型看到的画面。项目在任务 reset 中清理窗口与浮层，并增设与成功判据相反的 `precondition`；起点不成立的轮次记为无效，不计入成功率。客机关闭记事本会话恢复，并取消固定曾引出登录框的 Copilot。完成结果由进程、窗口标题或文件副作用判定，同时保留模型自报 `done`，两者不再混为一谈。这些调整涉及环境、判定和提示词，不能把最终数字全部归功于 LangGraph 编排。

| 任务 | 遇到的问题 | 项目实际修改及作用 |
|---|---|---|
| 打开浏览器 | 留存的 Edge 进程会让“已运行”判据在动作前就满足；旧批虽有 5/5，但平均约 6 步。 | 每轮先结束旧 Edge、清理桌面，开跑前确认 `msedge.exe` 不在运行，完成后确认进程出现。另做桌面图标双击路径的定点验证，确认双击执行器本身能启动 Edge；没有为这项单独增加专用动作捷径。 |
| 搜索指定内容 | 旧标题条件仅含“Python”，曾误匹配评测控制台；规划器把点击已聚焦地址栏单独列为子任务，截图几乎不变，导致反复点击而未输入搜索词。曾见搜索框进入旧剪贴板文本。 | 判定器排除控制台并收紧为 `Python.*Edge`；规划器把聚焦地址栏与输入查询词组成有可见结果的目标；执行器推迟恢复剪贴板，减少粘贴旧内容的时序风险；清理 Copilot 干扰。剪贴板机制与现象相符，但不能仅凭截图认定它是唯一原因。 |
| 打开指定文件 | 路径曾被输进记事本正文，或在“打开”对话框重复输入；旧标签页可能使目标标题已存在，但对话框仍开着。另一轮在同一坐标反复点击、未输入路径。 | 关闭会话恢复；起点确认目标文件存在且旧记事本退出；终态要求精确目标标题、记事本进程存在且“打开”对话框消失，并检查前台模态窗口。执行器仅允许在正确文件对话框输入绝对路径；`planner_v8` + `executor_v5` 在文件名框已有焦点时直接输入，连续无变化点击反馈并停止，`done` 仍须通过终态检查（关键修复 `63cf0ab`）。 |
| 发送消息 | 记事本残留曾抢焦点，文字输错窗口；未聚焦输入框时重复输入，触发安全哨兵。模拟程序按回车就发送，旧计划继续点发送按钮有重复提交风险。 | 重置本地模拟程序和日志；规划器要求先聚焦输入框、再输入、只提交一次，以消息列表出现作为可见终点；判定从“日志包含文字”改为 `messages.log` 中“你好世界”**恰好一次**。该任务不向真人发送消息。 |
| 关闭应用 | 旧 reset 没打开计算器时，“进程已退出”会在任务开始前被误判成功；旧进程残留也可能跨轮累积，UWP 冷启动超过固定等待时间会使起点无效。 | reset 先结束旧 `CalculatorApp.exe`，重新启动并轮询等待进程出现；开跑前要求计算器运行，完成后要求进程退出。因此画面中计算器先打开又关闭，是这一任务的预期流程。 |

最终同批控制台为五项各 **5/5**。搜索、打开文件、发送消息经历了针对动作顺序与判定的实质修复；打开浏览器和关闭应用主要补强了评测起点与终态可靠性。历史单轮复测和早期批次使用不同代码、提示词及桌面状态，不能与最终批次组成严格单变量“修复前后提升”。提交与轨迹索引见[阶段性结果汇报](20261006-阶段性结果汇报.md)“五项基础任务的主要问题与修改经过”。

### 4.4 为什么五项基础任务通过，20 项测试仍表现不佳

五项基础任务的通过，验证了**五条经过多轮排障和针对性修复的操作路径**；20 项测试则要求系统处理新增的文件编辑、连续输入和跨应用流程，暴露出中间状态判断与错误恢复的不足。20 项任务集**包含这五项**，且它们在第七周 20×1 探索批中再次各通过一次；表现不佳主要出现在新增任务，不能说原五项在该批次失效。打开指定文件虽平均要 12 步，也经历了文件对话框、焦点和终态检查等专门修复，因此不能仅以“基础任务步数短”解释 25/25。

| 比较维度 | 五项基础任务已验证的范围 | 新增任务暴露的要求 |
|---|---|---|
| 目标与调整 | 固定应用、固定文本或文件；搜索、打开文件、发送消息都有对应的规划和执行修复 | 重命名、删除、文件追加、跨文件复制、计算后保存等路径，没有逐项达到同等程度的反复修复与验证 |
| 中间状态 | 起点 reset、部分前台窗口保护和最终进程/窗口/日志判据覆盖了主要故障 | 必须确认选中文件、正文焦点、保存结果、计算器操作数与运算符等中间状态；现有循环多依赖模型自报子任务完成 |
| 错误恢复 | 已知的无效点击、错误对话框和重复发送有针对性拦截 | 新界面偏离原计划后通常继续沿旧计划执行；旧版复杂任务还受 8 条子任务截断影响 |
| 证据范围 | `qwen3-vl-8b-instruct`、`planner_v8 + executor_v5` 的一次统一 5×5，客机控制台 25/25 | 探索批仅启动 14 项；第 15–20 项后来在不同提交下各单跑一次，不能拼成同条件 20 项成功率 |

这种差异说明：**已有修复对已知任务有效，但不能自动提供通用的中间状态验证和错误恢复能力**。新增任务的失败也不能一概归因于模型；必须同时检查计划、单步动作、反馈、桌面环境和评测判据。表内关系是系统结构与观察到的轨迹相结合的解释，不是单变量对照实验。

### 4.6 操作案例：计算器为什么没有算出并保存结果

第 18 项要求在计算器输入 `123 + 456 =`，再把 `579` 写入记事本并保存。首次单跑时模型给出 13 条计划，旧上限只保留 8 条；这解释了部分后续目标为何不在计划内，**但不能解释全部失败**。放宽到 16 条后的首次复测仍为 **0/1**，轨迹与客机截图呈现了另一层问题：

| 环节 | 已观察到的情况 | 可确认的含义 |
|---|---|---|
| 已执行的按键 | 先正确点击 `1、2、3、+`，随后继续点击 `1、2、1、1、1、1` | 至少前四个控件被找到并触发；这轮没有证据表明主要问题是整屏鼠标坐标偏移 |
| 界面结果 | 截图显示上一操作数为 `123 +`，当前输入为 `121,111` | 模型没有在输入 `123 +` 后结束当前复合子任务，第二操作数也未成为预期的 `456` |
| 循环反馈 | 数字区确实变化，但每步全屏变化比例低于 `0.01` 阈值；最后四次同位置点击被重复保护停止 | 全屏帧差对局部数字变化不够敏感，刹车阻止继续重复，却不能自动修正错误数字；帧差不是已证实的错误点击唯一成因 |
| 任务终态 | `C:\agent-test\笔记.txt` 不存在 | 流程未到写入与保存阶段，不能称为仅在最后保存时失败 |

此例说明**规划与单步执行是两种不同的故障**。当前执行器每次根据截图和子任务描述决定下一动作，没有可靠的阶段状态确认“`123 +` 已输入完，下一步应转到 `456`”；中间子任务的模型自报 `done` 也没有计算器显示内容的程序化核对。即使加入“失败后重规划”，已经执行的错误数字若未被识别为错误，新计划仍会从错误界面继续。`planner_v12` 已把操作数与运算符拆开，但尚无对应客机成功实测，不回填为本次成绩。

## 五、主要经验与安全边界

1. **环境是实验变量。** 旧版同一模型在不同桌面残留状态下出现显著结果差异。任务级 reset、起点检查和程序化判定减少假成功；跨引擎结果应按各自环境和版本解释。
2. **可观测的子任务更容易形成反馈。** 只点击已聚焦地址栏几乎不改变画面，曾使搜索任务反复点击；将聚焦和输入合并、把完整路径输入放在正确文件对话框、对无变化点击设上限，是后期基础任务修复的核心。
3. **离线指标与实机成功不可互换。** W5 的离线准确率改善和客机 0/25 同时成立；W6 的 Reflector 表面提升与恢复率 0/30 同时成立。报告两面结果，避免单看有利指标。
4. **安全边界需要实述。** 键鼠仅在客机操作，但在线模型调用会上传截图。历史客机曾出现 Copilot 登录框、记事本打开环境文件和密钥误入仓库等事件；旧密钥已由用户撤销，新的 `.env` 放在客机用户目录并不再跟踪。客机曾有开发者账号与个人数据，不能宣称评测环境完全不含个人数据。急停和哨兵减少后续动作，不能保证第一下永不误点。

## 六、未来改进与系统验证展望

后续工作的目标是把针对五项基础任务积累的经验，提升为适用于不同应用和任务类型的共同能力。**泛化是验证结果，不是某项设计天然具有的属性**：即使一项改动修好了计算器，也需要在文件操作、消息发送和未参与调试的任务变化中观察到收益，才能说它具有迁移价值。根据本报告的失败证据，可从以下维度改进并验证。

| 维度 | 可泛化的改进方向 | 跨任务验证重点 |
|---|---|---|
| 任务拆解 | 将复合目标划为有明确阶段结果的操作，避免把多次输入、确认和保存混在同一阶段；复杂任务应完整保留必要步骤 | 同时检查计算、文件编辑和跨应用任务的阶段是否清楚、计划是否遗漏或截断 |
| 界面识别与定位 | 每次操作前核对当前窗口、输入焦点和目标控件，适应窗口位置与桌面状态变化 | 在旧窗口残留、窗口移动和不同初始焦点下，统计是否仍能作用于正确对象 |
| 动作效果与反馈 | 区分“点击或按键已发出”与“界面确实出现预期变化”；对小范围变化提供更敏感的观察 | 统计无效重复动作、有效动作被误判为无变化、首步实际起效等情况 |
| 阶段完成判断 | 对关键中间结果进行独立核对，减少零动作报完成和做完后继续操作 | 在计算结果、文件名、文件内容与消息出现次数上，分别统计过早和过晚结束 |
| 纠错与安全 | 确认偏差后根据当前状态有限次调整后续操作；对发送、删除等有副作用的动作控制重复执行 | 同时统计恢复成功、重复提交、误操作与急停；恢复不能以增加安全事件为代价 |
| 环境与模型口径 | 固定或记录桌面起点、分辨率、模型及提示词；将环境无效、接口错误和 GUI 执行错误分开 | 在相同条件下比较改进前后，并分别报告在线模型与本地微调模型的结果 |

验证应分三步进行。**先定位**：从脱敏轨迹和关键截图找出每轮的首次偏差，按规划、识别、动作、阶段判定、恢复、环境或外部接口分类；缺少证据时保留“原因未明”，不根据最终文件不存在倒推具体错误。**再做对照**：每次只改变一个共同机制，在相同模型与桌面条件下复测受影响的任务，同时运行原五项以检查回归。**最后检验迁移**：覆盖 20 项中的单步、多步、复杂三档，并加入未参与调试的文件名、窗口布局或起点变化；正式结果应采用每项多轮，而不是依据单次通过。

评价时同时报告最终成功率、关键阶段通过率、零动作报完成、重复无效动作、恢复成功、步数与耗时、安全事件及无效轮。只有改进在多类任务和未参与调试的变化中仍有效，且没有明显损害原五项或安全性，才能称为系统层面的提升。第 18 项计算器说明了这一顺序的必要性：重规划可以改变后续路线，但必须先可靠发现 `123 +` 之后输入已经偏离目标；单独增加重规划不构成操作能力改善的证据。本节是未来验证方案，**不计入已完成的实测成绩**。

## 七、最终结论

项目完成了可运行的 GUI 智能体原型、LangGraph 执行路径和五项基础任务的一批统一客机测试；形成了带程序化终态判定、轨迹与安全急停的评测框架。本地 3B 模型经微调后，离线动作类型准确率 **15.5%→59.7%**、全量命中率 **4.0%→49.1%**，但 `done` 误报增加，1024×768 受控客机一批任务为 **0/25**；这同时记录了模型的单步提升和端到端限制。后来的基础任务客机控制台 **25/25** 使用另一在线模型。五项基础任务经过针对性修复后，在其固定目标与判据内通过；新增任务暴露了计划粒度、单步动作、阶段完成判断和错误恢复的不足，计算器错误输入是其中可由截图核对的例子。第七周一批 20 项计划运行至第 14 项急停，后六项随后分别完成首次单跑；20 项均有实机尝试，但尚无同配置完整重复批次。所有数字均以对应模型、版本和实际执行批次为范围。
