### 几组值得点出的测试

**`test_data.py` 里的坐标口径测试。** 两个 loader 的坐标约定是不同的：

- `test_screenspot_v1_reads_bbox_as_normalized_xyxy`
- `test_screenspot_v2_reads_bbox_as_absolute_xywh`

同一个数据集的 v1 与 v2 一个用**归一化 xyxy**、一个用**绝对 xywh**。
这两条测试把口径钉死在测试里，而不是留在注释里——弄混了不会报错，只会让
所有坐标偏掉。

**`test_screenspot_v2_reports_unextracted_zip_instead_of_crashing`。**
图片包没解压时，loader 报告「未就绪 + 原因」而不是崩溃。数据集预处理是
一条长流水线，中途崩掉会让人不知道断在哪一步。

**`test_jsonl_round_trip_is_lossless`。** `UnifiedSample` 写进 JSONL 再读
回来必须逐字段相等。整条数据链下游（统计、划分、微调数据构建）都只认这个
结构，它有损就全线有损。

**`test_decoupled_prompts.py` 的 28 条。** 验证提示词模板与代码解耦——
换模板不改代码。第 5 周的提示词消融（8 个模板轮换）就建立在这条保证上。

### 跳过用例：0 条，但有一个条件跳过分支

`test_data.py:135` 有一条 `pytest.skip("缺少 parquet 引擎…")`。ScreenSpot v1
是 parquet 格式，没装 `pyarrow` / `fastparquet` 时这条测试自动跳过。

本次执行环境装了 `pyarrow 25.0.1`，**所以实际跳过 0 条**。在只装了
`requirements.txt` 第 1 段的最小环境里跑，这里会出现 1 skipped——那是预期
行为，不是失败。

## 4. 本报告不覆盖什么

**这一节比前三节重要。** 88% 很容易被读成「系统 88% 可靠」，那是错的。

### 4.1 全部 369 个用例都不碰真实模型

模型调用一律走 `llm/fake.py` 的 `ScriptedBackend` 替身：喂进去什么，它就
按脚本吐出什么。**所以这 369 条测试对「模型给出的答案对不对」提供的证据
是零。** 它们证明的是：**代码按设计工作**——请求组装正确、输出解析正确、
异常路径不崩、坐标换算不偏。设计对不对、模型答得对不对，都不在射程内。

这是单元测试应有的边界，不是缺陷。但读这份报告的人必须知道这条边界在哪。

### 4.2 数据 loader 只在内联的小样本上测

`test_data.py` 用 `tmp_path` 现造几条 JSON / parquet 记录来测三个 loader，
**不读真实数据集**（ScreenSpot-v2 的图片包 1.3GB、ScreenAgent 仓库需 clone）。

真实数据上的证据是另一件东西：`docs/数据集统计分析报告.md`，由
`scripts/prepare_datasets.py` 在完整数据集上跑出来——6,555 条样本、
3,973 张不重复截图、清洗保留率 100.0%。**那份报告是真实数据的证据，
这份报告是代码逻辑的证据，两者不能互相替代。**

### 4.3 是语句覆盖率，不是分支覆盖率

88% 指的是「有多少行被执行过」，不是「有多少条件分支的两侧都走过」。
一个 `if a and b` 只要走过一次就算覆盖，`b` 为假的路径可能从没测过。

### 4.4 不含性能、并发、长时间运行的验证

没有压力测试、没有内存泄漏检测、没有并发安全性验证。
