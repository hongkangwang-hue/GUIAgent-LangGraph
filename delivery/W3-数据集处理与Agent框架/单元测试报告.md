## 一、概述

第 3 周交付的核心是三个 Python 包——`data`（数据集处理）、`llm`（大模型调用
接口）、`agent`（Agent 框架），合计 6,790 行代码。为验证这三个包的正确性，
配套编写了 8 个测试文件、369 个测试用例。

本次执行结果：

> **369 个用例全部通过，无失败、无跳过；三个包的语句覆盖率为 88%。**

测试不依赖 GPU、不依赖网络、不依赖 API 凭据、不依赖真实桌面环境，因此
任何一台安装了 Python 3.10 与 pytest 的机器都可以复现，复现方法见第五节。

为确认交付压缩包本身完整，本次执行**先将交付包解压到一个全新的空目录，
再在该目录中运行**，而非在开发目录中运行——后者无法证明压缩包内容齐全。

## 二、测试范围

### 2.1 纳入统计的三个包

| 包 | 职责 | 对应大纲第 3 周任务 |
|---|---|---|
| `data` | 三个公开数据集的装载、清洗、统计与划分 | 任务 1 |
| `agent` | 任务规划、上下文管理、提示词模板、会话编排 | 任务 2、3 |
| `llm` | 大模型调用抽象，涵盖 API 调用与本地部署两条通路 | 任务 4 |

### 2.2 未纳入统计的五个包及其原因

交付包的 `src/` 目录下另有 `control`、`perception`、`core`、`grounding`、
`finetune` 五个包。它们分属第 2、4、5、6 周的工作，之所以随本包一并提供，
是因为上述三个包在导入时依赖它们——例如 `data/schema.py` 依赖
`perception.types` 中的坐标类型定义。若不提供，交付包将无法独立运行。

这五个包**不计入本报告的覆盖率统计**。原因是：它们的测试位于各自所属周次
的交付物中，若在此处一并统计，本周三个包的真实覆盖情况会被稀释，得到一个
无法解释的数字。该约定已写入 `pyproject.toml` 的覆盖率配置。

## 三、测试方法

### 3.1 外部依赖的处理方式

单元测试的一条基本要求是：在任何一台机器上都能在数秒内跑完，不能因为缺少
GPU、缺少网络或缺少凭据而无法执行。本项目涉及两类重量级外部依赖，分别按
如下方式处理：

**大模型调用。** 全部通过 `llm/fake.py` 中的 `ScriptedBackend` 替身完成。
该替身按预设脚本返回响应，使测试可以精确验证请求组装、输出解析、异常处理
等逻辑，而无需加载 8GB 的模型权重或调用付费 API。

**数据集读取。** 三个数据集的装载器（loader）测试均使用 pytest 的
`tmp_path` 机制，在临时目录中即时构造若干条 JSON 或 parquet 记录进行验证，
不读取完整数据集（ScreenSpot-v2 的图片包为 1.3GB，ScreenAgent 需从 GitHub
克隆仓库）。

需要说明的是，完整数据集上的验证由另一条路径完成：
`scripts/prepare_datasets.py` 在真实数据上运行后生成
`docs/数据集统计分析报告.md`，该报告中的 6,555 条样本、3,973 张不重复截图、
100.0% 清洗保留率等数字，即为完整数据集上的实测结果。

### 3.2 与真机验证的分工

需要真实硬件或外部服务的能力，由 `scripts/` 目录下的验证脚本承担，不属于
本报告范围：

| 脚本 | 验证内容 | 所需条件 |
|---|---|---|
| `verify_llm.py` | API 通路连通性 | API Key 与网络 |
| `serve_local_model.py` | 本地权重加载与推理服务 | GPU 与模型权重 |
| `prepare_datasets.py` | 完整数据集预处理流水线 | 约 2GB 磁盘空间与网络 |

## 四、测试结果

### 4.1 总体

```
369 passed in 4.01s
```

| 指标 | 数值 |
|---|---|
| 测试文件 | 8 个 |
| 测试用例 | **369**（通过 369 / 失败 0 / 跳过 0） |
| 被测语句 | 2,071 条 |
| **语句覆盖率** | **88%** |
| 执行耗时 | 4~7 秒 |

耗时之所以给区间而非定值：首次运行需要生成字节码缓存，约 7 秒；此后重复
运行约 4 秒。通过数与覆盖率是确定的，耗时会随缓存状态波动。

关于「跳过 0 条」需补充一点：`test_data.py` 中有三条测试带有条件跳过——
一条针对 ScreenSpot v1 的 parquet 读取（需 `pyarrow`），两条针对图表生成
（需 `matplotlib`）。本次执行环境这些依赖齐备，故三条均正常执行。

运行测试所需的依赖边界经过实测确认。方法是新建一个空的虚拟环境，按
`requirements.txt` 的分段逐步安装并观察结果：

| 安装范围 | 结果 |
|---|---|
| 仅第 1a 段（pytest / numpy / pillow / pyyaml） | 20 failed —— 缺 `langchain-core` 与 `opencv-python` |
| 加上第 1b 段 | **366 passed, 3 skipped, 0 failed** |
| 再加上第 1c 段 | **369 passed, 0 skipped** |

`requirements.txt` 已按此结论重新分段，并把各段的实测结果写在文件头部。

### 4.4 对三个较低覆盖率模块的说明

**`llm/qwen_vl_local.py`（62%）与 `llm/factory.py`（59%）。**
两者未覆盖的部分性质相同：前者是加载 4-bit 量化权重、执行推理、解析模型
输出坐标的代码段，后者是根据 `--provider` 参数构造真实后端实例的分支。
这些路径分别需要 GPU 与模型权重、API Key 与网络，按第三节所述的分工原则，
它们由 `serve_local_model.py` 与 `verify_llm.py` 两个脚本在真机上验证。
此处的低覆盖率是设计选择，不是遗漏。

**`data/loaders/screenagent.py`（77%）。**
这是三个数据集装载器中覆盖率最低的一个。未覆盖的代码主要为两类：一是
`KeyboardAction` 与 `WaitAction` 的参数提取分支，二是四个文件级容错分支
（标注文件无法解析、缺少分辨率字段、缺少截图文件名、截图文件不存在）。

这些分支在完整数据集上均已实际执行过——`docs/数据集统计分析报告.md` 中的
动作类型分布表即为其产物——但目前尚无单元测试固定其行为。这是一处已知的
测试缺口，记录在此。

pip install -r requirements.txt          # 十来个包，约 410MB，约 50 秒
