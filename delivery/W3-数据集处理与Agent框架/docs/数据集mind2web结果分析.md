# Multimodal-Mind2Web 截图尺寸分析与清洗阈值推导

> 数据源：`osunlp/Multimodal-Mind2Web`，train split
> 测量日期：2026-08-27
> 目的：为「ScreenAgent 为主、Mind2Web 为辅」的消融实验确定样本清洗阈值
> **阈值由实测分布 + 下游判据推出，不是预先指定的**

---

## 0. 一句话结论

**页高 ≤ 3000 px。** 全量 7775 条中保留 2830 条（36.4%），
目标元素缩放后高度 ≥14 px 的比例维持在 **77.9% ± 3.3%**（5 折实测）。

**它是当前设定下的一个合理折中，不是数学意义上的断点。**
见 §4.1 的误差分析——2500 与 3500 同样说得通。

---

## 1. 先记一次错判

在本次测量之前，我基于 **42 张抽样** 得出过一个结论：

> 「Mind2Web 里不存在『普通网页截图』这个群体。它的采集方式就是整页滚动截图
> —— 不是有些页长有些页正常，而是全部按整页拍。」

**这个结论被全量数据直接推翻。**

| 我当时说的 | 全量实测 |
|---|---|
| 宽高比 1.2~2 这一档：0 张（0%） | P10 宽高比 = **1.31**，正落在这一档 |
| 「不存在接近视口的截图」 | **P0 = P1 = 1080 px**，即 1280×1080 的一屏页面确实存在 |

失误原因不是判断错，是**样本量不足以看见那一档**。n=42 时一个占比 3~5% 的分箱
抽到 0 张属于正常波动，我却把它当成了「该群体不存在」的证据。

**留痕理由：这与 M2 阶段「按 X 铺开只保证 X 这一维无偏」是同一类错误——
用一个不足以支撑结论的样本去下全称判断。**

### 2.5 关键观察：**没有天然断点**

分布是**单峰 + 右长尾**，众数在 4k~5k，不是「普通网页」和「超长网页」两坨。

所以：

- 「剔除超长网页」在数据上**成立**——长尾确实存在（P99 = 18364 px，最长 44771 px）

**结论：阈值不能从直方图形状读出来，必须挂在一个下游判据上。**

## 3. 下游判据：目标元素缩放后还剩多少像素

### 3.1 判据来源

训练时图像会被压到 `max_pixels = 896×896 = 802816`：

```
缩放系数 = sqrt(max_pixels / (W × H))          （Qwen2-VL smart_resize 等效）
```

Qwen2-VL 视觉 patch 为 14 px，`merge_size = 2`，
**一个视觉 token 覆盖 28 px**。目标元素缩到 28 px 以下，
垂直方向连一个 token 都占不满，**视觉表示会显著变弱**。

> **这是风险指标，不是硬判定。** 模型仍可能借助周边文本、图标语义、
> 邻近布局和多 token 上下文完成定位。28px 用来给样本排序、比较不同阈值，
> 不用来断言某个样本「必然不可见」。

于是取两条线：

| 线 | 含义 |
|---|---|
| 元素高 ≥ 28 px | 占满一个视觉 token |
| 元素高 ≥ 14 px | 占半个视觉 token（可读下限） |

### 3.2 样本

抽 **1121 条**真实 `pos_candidates[0].bounding_box_rect`，
按 `idx` 均匀铺满 0~7775（60 批 × 20 条），不集中在开头。

### 3.3 目标元素本身就很扁

原图（1280 宽坐标系）中的目标元素尺寸：

| | P10 | P25 | 中位 | P75 | P90 |
|---|---:|---:|---:|---:|---:|
| 宽 | 37 | 79 | **160** | 275 | 408 |
| 高 | 18 | 24 | **37** | 49 | 62 |

缩放后：

| | P10 | P25 | 中位 | P75 | P90 |
|---|---:|---:|---:|---:|---:|
| 宽 | 14.2 | 29.3 | **68.2** | 125.1 | 193.6 |
| 高 | 6.3 | 9.9 | **15.2** | 21.5 | 29.5 |

**网页链接/按钮天生是扁的**——中位高度在原图里就只有 37 px。
这不是缩放造成的，缩放只是把它从「扁」变成「几乎不可见」。

## 4. 阈值推导

### 4.1 口径 A：按页高筛

| 规则 | 保留率 | 折算全量 | 元素高 ≥28px | 元素高 ≥14px |
|---|---:|---:|---:|---:|
| 页高 ≤2000 | 14.6% | 1137 | 35% | 79% |
| 页高 ≤2500 | 26.8% | 2081 | 26% | 81% |
| **页高 ≤3000** | **36.4%** | **2830** | 25% | **78%** |
| 页高 ≤3500 | 45.9% | 3572 | 21% | 75% |
| 页高 ≤4000 | 50.4% | 3919 | 19% | 72% |
| 不筛 | 100% | 7775 | 12% | 55% |

**先看误差，再谈阈值。** 各档的样本量不同，比例的标准误也不同：

| 阈值 | ≥14px | 子样本 n | 标准误 |
|---|---:|---:|---:|
| ≤2000 | 79% | 164 | ±3.2% |
| ≤2500 | 81% | 300 | ±2.3% |
| ≤3000 | 78% | 408 | ±2.0% |
| ≤3500 | 75% | 504 | ±1.9% |

**79 / 81 / 78 三个数互相都落在彼此的误差范围内**，78 → 75 的差也不显著。

所以数据支持的只有这一条：

- **3000 之后可读率单调下降**（78 → 72 → 70 → 66），趋势是真的
- **但拐点的具体位置没有被数据定住**——2500 或 3500 同样说得通

结论应表述为：

> 在当前 `max_pixels = 896×896` 与 Qwen2-VL 视觉预处理设定下，
> **页高 ≤3000 px 是一个合理折中**：保留约 36.4% 的训练动作样本，
> 同时把目标元素缩放后高度 ≥14 px 的比例维持在约 78%。

**不能写成「拐点」。** 写成拐点，就是又一次用不足以定位的样本下精确判断
（与 §1 记录的那次同类）。

### 4.2 口径 B：直接按缩放后元素高筛（页高不限）

| 规则 | 保留率 | 折算全量 | 中位页高 | 页高 P90 |
|---|---:|---:|---:|---:|
| 元素高 ≥14 | **54.4%** | **4231** | 2921 | 5429 |
| 元素高 ≥20 | 29.2% | 2268 | 2597 | 5234 |
| 元素高 ≥28 | 12.0% | 936 | 2173 | 4923 |

口径 B 保留下来的样本，页高分布：

```
 0k~2k   21.0%
 2k~4k   46.1%
 4k~6k   26.7%
 6k~8k    5.2%
8k~10k    0.8%
 >=10k    0.2%
```

### 4.3 选 A 不选 B

**B 在两个指标上都赢**：留下更多数据（4231 vs 2830），
且按定义 100% 可读（vs 78%）。

**但仍然选 A**，理由：

| | 口径 A（页高） | 口径 B（元素高） |
|---|---|---|
| 筛选依据 | 页面级属性，**与标签无关** | **按标签筛**——只留目标够大的样本 |
| 评估偏差 | 无 | 挑软柿子，未筛数据上评估会系统性偏乐观 |
| 与要求的一致性 | 就是「剔除超长网页截图」这条规则 | 是另一条规则 |

**B 是选择在结果上（selection on the outcome）。** 训完的模型在未清洗数据上
的表现会比清洗集上差，而我们无法区分这是「跨域难」还是「筛选造的假象」。

### 4.4 备选：A ∩ B

`页高 ≤3000 且 元素高 ≥14` —— 约 **2200 条**，
仍是 20% 混入需求（445 条）的 **5 倍**。

如果消融在纯 A 下是负结果，可以用这一档再试一次，
用来区分「跨域本身不行」和「清晰度不够」。

### 4.5 供给完全不是约束

混入 20% 到 1783 条 ScreenAgent 执行器样本，需要约 **445 条**。

| 口径 | 折算全量 | 是需求的 |
|---|---:|---:|
| 页高 ≤3000 | 2830 | **6.4 倍** |
| 元素高 ≥14 | 4231 | 9.5 倍 |
| 页高 ≤2000（最严） | 1137 | 2.6 倍 |

**即使卡到最严的 ≤2000 也够用。**

### 4.6 抽样稳定性（1121 条够不够）

把 1121 条按 `idx % 5` 分 5 折 —— 用取模而不是切连续块，
保证每折都均匀铺满全数据集。各折单独计算 `页高≤3000` 下的可读率：

| | ≥14 px | ≥28 px |
|---|---:|---:|
| 第 0 折 | 74.1% | 17.3% |
| 第 1 折 | 79.7% | 22.8% |
| 第 2 折 | 79.2% | 30.6% |
| 第 3 折 | 74.1% | 30.6% |
| 第 4 折 | 82.4% | 25.3% |
| **均值** | **77.9%** | **25.3%** |
| **标准差** | **3.3%** | **5.0%** |
| **极差** | 8.3% | **13.3%** |

**两个数的可靠性完全不同：**

- **≥14 px 的 78% 站得住**（±3.3%），足以支撑阈值之间的比较
- **≥28 px 的 25% 站不住**（±5.0%，折间 17% ~ 31%）

所以 §4.1 的阈值比较可以用 ≥14 px 这一列；
而「只有四分之一的目标能占满一个视觉 token」这句话
**只能作定性描述，不能当精确比例引用**。

> 这一节的存在本身是个提醒：**先验证再引用**。
> 若不做这个检查，25.3% 会以和 77.9% 相同的口吻被写进报告，
> 而它的误差是前者的 1.5 倍。

### 4.7 `pos_candidates[0]` 的代表性（初步）

1121 条样本中，第一个正候选的 tag 分布：

| tag | 条数 | 占比 |
|---|---:|---:|
| `a` | 341 | 30.4% |
| `button` | 272 | 24.3% |
| `input` | 203 | 18.1% |
| `label` | 64 | 5.7% |
| `div` | 52 | 4.6% |
| `li` | 46 | 4.1% |
| `span` | 45 | 4.0% |
| `select` | 42 | 3.7% |

**前三类占 72.8%，都是真正的可交互元素**，不是随机 DOM 节点。
这支持「第一个正候选即操作目标」，但**不构成证明**。

尚未做、应当补的：

1. 人工抽查数十条，确认第一个正候选确实对应该次操作
2. 多正候选的样本是否会让 bbox 尺寸统计偏移
3. CLICK / TYPE / SELECT 三类动作的候选结构是否一致

## 5. 一个必须先说的不利事实

```
即使卡到 <=3000：
  元素高 >=14px    77.9% ± 3.3%     这个数稳
  元素高 >=28px    25.3% ± 5.0%     **这个数不稳，折间 17% ~ 31%**
  缩放后中位高      19.9 px

对照 ScreenAgent：1024 × 768 = 786432 <= 802816 → 缩放系数 1.00
```

**28px 那个数不要当精确值用。** 5 折交叉里它从 17.3% 跳到 30.6%，
极差 13 个百分点（详见 §4.6）。可以说「大约四分之一」，
不能说「25%」。

**这里要对照的不是分辨率，是预处理之后的元素尺度。**
ScreenAgent 的 1024×768 不触发缩放，所以它的元素以原尺寸进入模型；
Mind2Web 即使卡到 ≤3000 也要缩到约 0.5。

> **不能由此推出「Mind2Web 必须裁到和 ScreenAgent 同分辨率」。**
> 最终推理环境是客机的 1920×1080，与 1024×768 本来就不同；
> 模型内部还会再做一次 smart resize。真正决定 grounding 难度的是
> **预处理之后目标元素还剩多少视觉尺度**，不是原图分辨率是否对齐。

这个尺度差距**清洗只能缓解、不能消除**——它来自两个数据集采集方式的
根本差异（桌面截一屏 / 网页截整页）。

**所以消融很可能是负结果。** 这不是实验设计的问题：
「效果差就不纳入」这条判定规则正好接得住这种情况。

**预先写下这个预期，是为了避免事后把负结果解释成别的原因。**

## 6. 一个必须报出来的混杂变量

train split 只有三个 domain：

| domain | 条数 | 中位高度 | ≤2000 | ≤3000 | ≤4000 |
|---|---:|---:|---:|---:|---:|
| Travel | 4082 | 3738 | 18% | **36%** | 54% |
| Shopping | 2309 | 4962 | 11% | **23%** | 37% |
| Entertainment | 1384 | 4204 | 13% | **28%** | 45% |

**Shopping 页面天生更长**（中位 4962，比 Travel 高 1224 px），
按高度卡会系统性少收 Shopping。

### 6.1 清洗前后的 domain 分布（全量实测）

| domain | 原始 train | 页高 ≤3000 | 变化 |
|---|---:|---:|---:|
| Travel | 4082（52.5%） | 1483（61.9%） | **+9.4%** |
| Shopping | 2309（29.7%） | 529（22.1%） | **−7.6%** |
| Entertainment | 1384（17.8%） | 382（16.0%） | −1.8% |

### 6.2 清洗前后的动作分布（全量实测）

| 动作 | 原始 train | 页高 ≤3000 | 变化 |
|---|---:|---:|---:|
| CLICK | 6513（83.8%） | 1893（79.1%） | −4.7% |
| TYPE | 936（12.0%） | 386（16.1%） | +4.1% |
| SELECT | 326（4.2%） | 115（4.8%） | +0.6% |

**动作配比确实变了，但幅度约为 domain 变化的一半**（4.7 vs 9.4 个百分点）。

TYPE 占比上升符合直觉：表单页、搜索页天生比长列表页短，
按高度筛选会相对多留下它们。

**两张表都必须进正式报告。** 否则「加了 Mind2Web」这个变量里同时混着：

1. 网页视觉数据的引入
2. domain 配比变化（主要）
3. action 配比变化（次要）

### 6.3 SELECT 没有对应动作 —— 这是个契约问题

本项目的动作空间（`data/schema.py` 的 `ACTION_REQUIREMENTS`）是：

```
left_click  double_click  right_click  mouse_move
scroll      type          key          wait   done   plan
```

**里面没有 `select`。** 而清洗后的 Mind2Web 有 **115 条 SELECT（4.8%）**。

这批样本只有三条出路：

| 做法 | 后果 |
|---|---|
| 直接丢弃 | 少 4.8% 数据，且**动作分布再次改变**——第三次改变 |
| 映射成 `left_click` | 语义不符：SELECT 是下拉框选值，不是点一下 |
| 扩充动作空间加 `select` | 客机上没有对应执行器，**推理端接不住** |

> **「动作空间是提示词与数据之间的契约。」**
> 改一边而不改另一边，另一边会静默地和它对着干 —— 本项目已经踩过这个坑
> （`SYSTEM_PROMPT` 只列 4 个鼠标动作，而 70% 的训练目标是 type/key/done）。

**倾向：直接丢弃，并把丢弃后的动作分布作为第三张表报出来。**
理由是另外两条要么引入语义噪声，要么让训练与推理不同构。

**这一条在混入方案定稿前必须先决定**，它会改变实际可用的样本数
（2394 → 2279）和动作配比。

## 7. 混入方式必须先定死

**「混入 20%」有两种做法，它们是不同的实验。**

```
做法 a   1783 + 445 = 2228 条     总量变大，步数变多
做法 b   1338 + 445 = 1783 条     总量不变，桌面数据被换走 445 条
```

| | 做法 a | 做法 b |
|---|---|---|
| Model B 更好时的解释 | **网页数据有用** 或 **单纯训得更久**，无法区分 | 网页数据有用 |
| 代价 | 混入了「数据量」这个变量 | 桌面训练数据少 25% |

**本方案采用做法 b。** 要回答的问题是
「网页数据对桌面能力有没有正迁移」，不是「更多数据有没有用」。

被换走的 445 条 ScreenAgent 样本**必须按动作类型分层抽取**，
否则会同时改变桌面数据自身的动作配比 —— 那就又多了一个混杂变量。

> 这一条不先定死，Model A vs B 跑完也解释不了结果。

## 8. 消融实验设计

```
档 A   ScreenAgent only                                  基准（尚未跑出）
档 B   ScreenAgent + Mind2Web(页高<=3000) 混入 20%
```

判定规则（沿用「一主一副」的思路）：

- 定位成功率**优于**档 A → 纳入
- 定位成功率**劣于或持平**档 A → 不纳入，记录负结果

补充要求：

1. **单变量**——只改数据，超参数与档 A 完全一致。
   `TrainingArguments` 未显式写 `seed`，靠 transformers 默认值 42，
   **应改为显式写死**，否则换版本就可能变。
2. **评估集只用桌面。** Mind2Web 是手段不是目的；
   评估集里若混入网页样本，档 B 赢了也说明不了桌面能力变强。
3. **报出清洗前后的 domain 分布与动作分布**（见 §6）
4. 若为负结果，可再跑一档 `A ∩ B`（§4.4）作**诊断性实验**，
   用于区分「网页域本身没帮助」和「目标元素过小拖累训练」。
   **诊断实验不覆盖主消融结论。**

## 9. 复现

### 9.1 数据获取

不下载任何图片本体，只取 HF datasets-server 的列元数据：

```python
# 全量尺寸（7775 条）
"https://datasets-server.huggingface.co/rows"
"?dataset=osunlp%2FMultimodal-Mind2Web&config=default&split=train"
"&columns=screenshot,website,domain,annotation_id"
"&offset={offset}&length=100"
# screenshot 列返回 {"src":..., "height":..., "width":...}

# bbox 抽样（1121 条）
"&columns=pos_candidates,screenshot&length=20"
# pos_candidates[0].attributes.bounding_box_rect = "x,y,w,h"
```

注意事项：

- `length=100` 时会撞 **HTTP 429**，需指数退避重试
- 拉 `pos_candidates` 时载荷大，`length` 降到 20
- 全量拉取约需 12~15 分钟，建议做断点续传（按已有最大 `idx` 续）

## 10. 本文档不声称的事

- **不声称 3000 是唯一正确的阈值。** 它是在
  「`max_pixels=896²` + Qwen2-VL 28px token」这一组具体设定下推出来的。
  换 `max_pixels` 或换模型，这个折中点会移动。**它也不是拐点**——
  §4.1 的误差分析表明 2500 / 3500 同样在数据支持范围内。
- **不声称 1121 条 bbox 抽样等同全量。** 高度分布是全量（7775），
  但元素尺寸是抽样（14.4%）。§4 的可读率数字带抽样误差。
- **不声称 `pos_candidates[0]` 一定是真实目标。** 取的是第一个正候选。
  §4.7 给出了 tag 分布作为间接证据（前三类 a / button / input 占 72.8%，
  都是真正的可交互元素），但**人工抽查尚未做**。
- **不声称清洗后 Mind2Web 一定有用。** §5 已写明预期偏负，
  结论以消融实验为准。
