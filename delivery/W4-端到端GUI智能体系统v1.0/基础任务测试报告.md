# M2 基础任务测试报告

> 5 个基础任务 × 5 次实测。对应 M2 交付物 10 与验收标准 2、3、5。
> 全部数据来自客机内实机执行，原始记录在 `docs/m2-runs/`。
> 撰写日期 2026-08-24。

---

## 摘要

在隔离虚拟机内跑通了「自然语言指令 → 任务拆解 → 逐子任务 Agent Loop →
程序化判定」的完整链路，5 个基础任务的成功率为 **19/24 = 79%**。

但这份报告最该被记住的不是 79%。**同一套代码、同一个模型，在一天之内
测出过 44%、75%、79% 三个数**，差异全部来自评测环境而非模型。下面第 3 节
逐次说明每个数字是怎么来的、之间改了什么。

三个有价值的定量结论：

1. **模型的自我判断与任务实际状态无关**——不是偏乐观，是无关。脏环境下
   它自报完成 20/25 而实测 11/25（高估）；干净环境下自报 16/24 而实测
   19/24（低估）。两个方向都错过。
2. **重复动作占总步数的 33%**，最长同一动作连发 12 次。成功率掩盖了这件事：
   `打开指定文件` 5/5 满分，却用了理论下限约 3 倍的步数。
3. **单步延迟的 85% 是 API 调用**，而 API 延迟在凌晨与上午之间相差 **8.97 倍**
   （1257ms → 11277ms/步）。执行与截图两段几乎不变。

## 1. 实验设置

| 项 | 值 |
|---|---|
| 执行环境 | VMware 虚拟机，Windows 11 中文版，1920×1080，4 vCPU / 12GB |
| 规划模型 | `qwen3-vl-8b-instruct`（阿里云百炼） |
| grounding | 模式 A（`NativeGrounding`，坐标由规划模型直接给出） |
| 坐标系 | 模型输出归一化到 [0,1000)，经 `CoordinateScaler` 转真实像素 |
| 上下文策略 | `ContextPolicy(k=3, full_res_steps=1, image_steps=2)` |
| 步数上限 | **每子任务** 6–12 步（不是每任务，见 §7.3） |
| 判定方式 | 程序化：进程 / 窗口标题 / 文件内容 |

**Agent 的一切键鼠执行只发生在客机内**，宿主机不受控制（M0 全局约束 1）。

### 任务集

| 任务 | 指令 | 判据 |
|---|---|---|
| `open_browser` | 打开 Microsoft Edge 浏览器 | 进程 `msedge.exe` 在运行 |
| `search_content` | 打开 Edge，在地址栏搜索「Python 官方文档」 | 进程 + 窗口标题匹配 `Python.*Edge` |
| `open_file` | 用记事本打开 `C:\agent-test\测试文档.txt` | 进程 `notepad.exe` + 标题含「测试文档」 |
| `send_message` | 在「测试消息」程序里发送一条内容为「你好世界」的消息 | `messages.log` 含「你好世界」 |
| `close_app` | 关闭计算器窗口 | 进程 `CalculatorApp.exe` **已退出** |

`send_message` 的操作对象是自写的本地模拟程序（`tasks/mock_messenger.py`）。
不用真实聊天软件的原因是它会同时踩两条 M0 约束：需要登录真实账号，
且会向真人发出不可撤销的消息。该程序是 tkinter 自绘界面，**UIA 读不到
子控件**，对 Agent 而言是纯视觉目标。

### 为什么判定必须程序化

M2 任务 8 写死了这条。本次实测给出了它的直接证据：若以模型自报的 `done`
为准，脏环境那一轮的成功率会是 80%（20/25），实测是 44%（11/25）。

## 2. 主结果

| 任务 | 程序化判定 | 模型自报完成 | 平均步数 | 理论下限 | 平均耗时 |
|---|---|---|---:|---:|---:|
| 打开浏览器 | **5/5** | 5/5 | 6.0 | ~2 | 14.8s |
| 打开指定文件 | **5/5** | 5/5 | 14.8 | ~5 | 35.2s |
| 关闭应用 | **5/5** | 5/5 | 2.0 | 2 | 6.8s |
| 发送消息 | **4/4** | 1/4 | 21.8 | ~4 | 289.1s |
| 搜索指定内容 | **0/5** | 0/5 | 14.0 | ~5 | 44.4s |
| **合计** | **19/24 = 79%** | 16/24 = 67% | | | |

**样本量说明。** `发送消息` 为 n=4：第 2 轮执行期间操作者碰了鼠标，
窗口焦点被改动，该轮已在存档中标记 `excluded` 并排除出分子分母
（**标记而非删除**——删掉的话没人知道这一批从 5 轮变成了 4 轮）。

**数据来源说明。** 前四行来自 `20260824-003649-all-exec.json`（00:36 全量），
`发送消息` 来自 `20260824-100516-send_message-exec.json`（10:05 补跑）。
补跑的原因见 §3.4。两批的环境配置一致，但 **API 延迟相差 8.97 倍**，
因此耗时一列不可跨批比较（§4）。

### 单步任务与多步任务的分界很清楚

`关闭应用` 2.0 步、`打开浏览器` 6.0 步，都是单步或近单步任务，5/5 满分。
一进入多步，步数就涨到 14–22，是理论下限的 3–5 倍。

**链路本身没问题**——感知、坐标转换、动作执行、判定四层都工作正常，
185 次点击全部由 `NativeGrounding` 直接给出坐标，grounding 段耗时合计
0.00ms，无一次定位失败。**瓶颈全部在规划层与反馈闭环。**

## 3. 四次测量：为什么一个数字不够

这一节是本报告的主体。同一套代码在一天之内给出三个成功率，
差异全部来自评测环境。

| 轮次 | 时间 | 成功率 | 零动作报完成 | 这一轮之前改了什么 |
|---|---|---|---|---|
| R1 | 08-23 22:5x | 13/25 = 52%* | — | 首次实机 |
| R3 | 08-24 00:09 | **11/25 = 44%** | 49/101 = 49% | 加 reset 清场（关闭其它应用） |
| R4 | 08-24 00:36 | **15/20 = 75%** | 0/65 = **0%** | 关掉记事本会话恢复、任务栏取消固定 Copilot、加 `reset_desktop.py` |
| R5 | 08-24 10:05 | 4/4 = 100% | 3/24 = 13% | 仅补跑 `send_message` |

\* R1 原始输出报 56%，其中一次是假成功，见 §3.1。

### 3.1 R1：判定器匹配到了评测脚本自己

`搜索指定内容` 第 5 次被判成功，命中的窗口标题是：

```
命令提示符 - python  scripts\run_basic_tasks.py --execute --repeats 5
```

判据是「标题含 `Python`」，而运行评测的那个命令行窗口标题里就有 `python`。
那一轮 Edge 根本没搜出来，`loop_status=subtask_failed`，模型自己都报了
没做完，判定却打勾。

**危险的是它看不出来**：`detail` 里写的是「窗口标题命中 …」，格式完全正常，
不逐条读标题内容根本发现不了。成功率因此从 52% 虚报成 56%。

修法两层：`check_window_title` 跳过本进程的控制台窗口（`GetConsoleWindow`）；
`search_content` 的 pattern 收紧成正则 `Python.*Edge`。

> **教训：评测工具必须看不见自己。** 判定器读的是全局状态，
> 而评测进程本身也在那个全局状态里。

### 3.2 R3：桌面残留把 44% 压在那里

R3 加了「reset 时关掉其它应用」之后，成功率不升反降（52% → 44%），
零动作报完成高达 49%。逐条查轨迹后发现三种 `taskkill` 够不着的残留：

**① 记事本的会话恢复。** Windows 11 的记事本会恢复上次会话，连同未保存
内容一起。某一轮 Agent 误开了 `.env`，此后每一轮 reset 杀掉记事本、
Agent 重新启动它，记事本就把 `.env` 那个标签页恢复出来。
`打开指定文件` 因此连续 5 轮面对错误的起点。

**② 开始菜单等系统浮层。** 不属于任何可杀的进程。

**③ 帐户登录模态框。** 任务栏上 Microsoft 365 Copilot 紧挨着 Edge，
模型点岔一次就拉起一个登录框，此后它一直挂在屏幕上。

第三种最贵，它让 `搜索指定内容` 连续四轮以**完全相同**的方式失败——
17 步、同一个终止原因。轨迹片段：

```
#1  点任务栏 (509,973)  → 那个位置不是 Edge，是 Microsoft 365 Copilot
#3  「Edge 已经在前台运行」 → done
#5  「当前屏幕是 Microsoft 365 登录界面，子任务目标未达成」 → done
#6–#17  对着登录框按了 12 次回车
```

**这些都是实验设计错误，不是模型能力问题。** 上一轮遗留的窗口是下一轮
输入的一部分，不清掉，5 次之间就不独立，成功率不可比。

### 3.3 R4：只改环境，44% → 75%，零动作 49% → 0%

R4 之前做了三件事，**代码逻辑一行未改**：

- 关闭记事本的「打开上次会话中的内容」
- 从任务栏取消固定 Microsoft 365 Copilot
- reset 第一条统一改为 `tasks/reset_desktop.py`（Esc 关浮层、Win+D
  最小化全部窗口、杀掉不属于测试环境的常驻应用）

结果：

| | R3 | R4 |
|---|---|---|
| 成功率 | 44% | **75%** |
| 零动作报完成 | 49/101 = 49% | **0/65 = 0%** |
| `打开指定文件` | 2/5 | **5/5** |

**零动作报完成从 49% 降到 0%，是本次实测最强的单一信号。**

它推翻了一个我们一度写下的判断。R3 的轨迹里有这样的片段：

```
#4 thinking「记事本窗口并未打开，因此无法点击记事本的文件菜单」  → {"done": true}
#5 thinking「文件菜单中的'打开'选项并未可见。因此，子任务目标未达成」→ {"done": true}
#6 thinking「没有文件对话框，因此无法输入路径。子任务目标未达成」  → {"done": true}
#7 thinking「没有正在加载文件的界面，子任务目标无法执行」          → {"done": true}
```

据此很容易断言「模型的 `done` 字段与推理脱节」，并把它当作模型的固有缺陷。
**但干净环境下它一次都没再出现。** 准确的说法是：

> 模型**只在屏幕上是它无法处理的东西时**才会零动作报完成。
> 起点干净时，它老老实实一步步做。

这个区别直接改变了改进的优先级：原本准备把「不接受零动作 `done`」列为
后续里程碑的第一优先，现在它的收益要重估——干净环境下它拦不到任何东西。
**真正该优先的是环境隔离。**

### 3.4 R5：`send_message` 的四次测量与 precondition 的作用

`send_message` 在四轮里给出 **0/5、0/5、全部无效、4/4**。

R4 的那 5 轮被判为**无效轮**——「测试消息」窗口不在了（程序被关掉）。
这是 `precondition` 机制第一次实战生效：reset 之后、Agent 之前先验一次
起点，没建立的轮次记 invalid，**既不进分子也不进分母**。

没有这个机制的话，这 5 轮会被记成 0/5 失败，合计从 15/20 = 75% 变成
15/25 = 60%，而且**从数字上完全看不出来那是环境没准备好**。

R5 单独补跑这一个任务，4/4 全通。

## 4. 延迟分解

M2 验收标准 3 要求按 API / grounding / 执行 / 截图 四段分解。

| 分段 | R4（00:36，20 轮 184 步） | R5（10:05，4 轮 87 步） | 变化 |
|---|---:|---:|---:|
| **API 调用** | 1257 ms/步 | **11277 ms/步** | **8.97×** |
| 动作执行 | 378 ms/步 | 473 ms/步 | 1.25× |
| 截图 | 131 ms/步 | 168 ms/步 | 1.28× |
| grounding | 0.00 ms | 0.00 ms | — |
| **单步合计** | **2.75 s** | **13.29 s** | 4.83× |
| API 占单步耗时 | 45.7% | **84.9%** | |

同一台机器、同一份代码、同一个模型，**只有 API 那一段变了 8.97 倍**。
两批之间唯一的差别是时间：凌晨 00:36 与上午 10:05。

三条推论：

1. **优化截图毫无收益。** 131ms/步 占 4.8%，而 M1 已把取帧压到 0.043ms——
   这里的 131ms 主要是 `fresh=True` 等待新帧的时间，不是取帧本身。
2. **grounding 段恒为 0.00ms**，因为模式 A 下坐标由规划模型随动作一起给出。
   这是模式 B 对照的基线值：模式 B 会把这一段从 0 变成 1–3 秒的本地推理，
   换取送 API 的截图可降分辨率。
3. **云端 API 延迟是评测中的不受控变量。** 这直接影响后续的提示词消融：
   要跑 45 次执行，若版本 1 跑在凌晨、版本 3 跑在白天，光时段差异就能
   造出 4.8 倍的「性能差距」。已写进 `docs/m3-执行计划.md`。

## 6. 五类失败模式

每一类都有轨迹原文佐证，轨迹 ID 可用 `python -m cli replay <id> --raw` 复现。

### F1 环境残留（4 种形态）

见 §3.2。修复后成功率 44% → 75%。**属于实验设计错误，不是模型问题。**

四种形态：会话恢复（状态在磁盘）、系统浮层（不属于任何进程）、
模态对话框（`taskkill` 碰不到）、上一轮遗留窗口。

### F2 零动作报完成

子任务以 `done` 收尾，一个动作都没执行成功。**由 F1 触发**：
脏环境 49%，干净环境 0%。见 §3.3 的轨迹原文。

典型形态是 thinking 明确写着「子任务目标未达成」而输出仍是 `{"done": true}`
——**推理正确，输出字段错误**。这一点对改进方向有直接影响：
该做的是约束输出，不是加强感知。

### F3 连续重复同一动作

占总步数 33%，最长连发 12 次。最纯粹的一例
（`traj-20260824-002840-4cd872`，第 3–14 步）：

```
#3  left_click (185,64) → 屏幕 (355,69)
    thinking「地址栏位于浏览器顶部，当前处于聚焦状态，点击即可激活输入」
#4  同上，一字不差
…
#14 同上，一字不差
```

同一坐标、同一句 thinking、原始输出逐字节相同。机制是：

> 点击一个已经聚焦的元素 → 屏幕无可见变化 → 模型收到相同输入
> → 输出相同动作。**确定性函数卡在不动点上。**

`ContextPolicy.k=3` 的历史窗口没能打破它——模型是**看着自己刚点过三次、
还是原样再点一次**。这决定了改进方向：不是加大上下文，而是外部打断
（帧差检测到界面未变即强制换策略）。

### F4 不可观测的子任务导致死循环

**`搜索指定内容` 0/5 的直接原因**，也是本次诊断中最根本的一条。

该任务的拆解是：

```
1. 双击桌面的 Microsoft Edge 图标
2. 点击浏览器地址栏          ← 卡死在这里
3. 输入文字"Python 官方文档"
4. 按回车键提交搜索
```

判定详情显示 Edge **确实启动了**（`msedge.exe` 找到 8 个），但标题停在
「新建标签页 - 用户配置 1 - Microsoft Edge」，从头到尾没搜过。
Agent 在子任务 2 上点了 12 次地址栏，撞上步数上限，`subtask_failed`，
整条轨迹终止——**子任务 3、4 根本没跑到**。

排查过程中曾怀疑是执行层的双击不奏效，写了 `scripts/diagnose_doubleclick.py`
做定点验证：`Win+D → doubleClick`、`单击 → doubleClick`、`单击 → 回车`
三条路径均成功启动 Edge。**双击没有问题。**

根因是子任务本身：

> **点击地址栏在屏幕上几乎没有可见变化。** 光标闪一下、边框微微高亮，
> 模型从截图里判断不出「我点中了吗」，于是做了唯一合理的事——再点一次。

对照 `打开浏览器` 5/5：那个子任务完成时**会出现一整个窗口**，一眼可见。

结论：**拆解出的子任务必须是「完成后屏幕上看得出来」的。**
「点击地址栏」不是可观测目标；「在地址栏输入 X」是（文字会出现）。
这两个子任务应当合并。

### F5 计划与应用实际行为错配

`发送消息` 的拆解里有独立的「点击发送按钮」子任务，而
`mock_messenger.py` 的输入框绑定了回车即发送：

```python
self.entry.bind("<Return>", lambda _event: self.send())
```

于是 Agent 在「输入文字」子任务里打完字按回车，消息已经发出；
进入「点击发送按钮」子任务时它还得再发一次。**每轮多发一条。**

判据是「日志含『你好世界』」，发一次和发五次都算成功，所以这个任务
仍是 4/4——**但代价是 21.8 步，理论下限约 4 步**。

Planner 拆任务时看不到「这个输入框回车即发送」这件事。这是一类
`milestone-4` 的 E1–E8 预期分类中**没有覆盖**的错误，建议补为 E9。

## 7. 方法论结论

### 7.1 评测工具必须看不见自己

见 §3.1。判定器读的是全局状态，评测进程本身也在那个全局状态里。
这次是窗口标题，同类风险还有：进程名匹配到评测脚本自己的 Python 进程、
文件判据读到评测脚本刚写的临时文件。

### 7.2 任务级 reset 清不干净桌面，M5 必须上快照

四次修复，四种新残留。修完记事本会话恢复冒出开始菜单，修完开始菜单
冒出模态登录框。**这不是「再修一次就好了」，是覆盖面推不到头。**

`milestone-5` 现在写的是「逐个验证重置脚本能把环境恢复到一致初始状态」。
本次实测证明做不到。**20 任务 × 3 次 = 60 轮的正式评测应改用虚拟机
快照恢复。** OSWorld 那类工作用整机快照做 reset，不是因为它慢得可以接受，
是因为任务级 reset 清不干净。

### 7.3 步数上限是「每子任务」，不是「每任务」

`max_iterations` 的计数在 `run_subtask` 内部，而 Session 对每个子任务
各跑一遍 Loop。所以「上限 6 步」的任务会跑出 8 步。这不是 bug，
但提示文案曾有歧义，已改为「每子任务上限 N 步」。

对排期的影响：一个拆成 5 个子任务的计划，步数上界是 5×12=60 而不是 12。
`Session` 里「子任务失败即停」的早退是实际的兜底。

### 7.4 四个「假指标」的共同形态

本项目至今出现过四次指标失真，四次里三次是低估：

| # | 指标 | 假值 | 真值 | 原因 |
|---|---|---|---|---|
| 1 | M1 召回 IoU | 10% | 100% | 人框标注的画法 |
| 2 | OCR 中英混排 | 86.7% | 100% | 空白符归一化 |
| 3 | 模式 B 字段完整率 | 85.7% | 100% | 分母算错 |
| 4 | `打开指定文件` 成功率 | 0% | 100% | 记事本会话恢复 |

外加本次的 `搜索指定内容` 假成功（高估）与统计脚本取错字段名
（把「相邻两步都是 `done`」统计成「重复动作」，得出一个看着合理的 13%）。

共同形态：**都不报异常，只安静地给出一个像模像样的错数。**
GUI Agent 的评测里，「环境是否真的回到了初始状态」「判据是否真的在测
你以为的东西」比模型本身更容易出错，而且错了看起来完全像模型能力问题。

### 7.5 一个安全事件

实测过程中 Agent 两次访问到仓库里的 `.env`，第二次**修改并保存了它**——
`LLM_PROVIDER` 的值被写成了 `dashscope你好世界测试消息你好世界…`。

机制：记事本会话恢复把 `.env` 拉回前台 → Agent 误判焦点 → 「你好世界」
输入落进去 → 被保存。

这一轮恰好改到的是不影响评测的字段（执行脚本显式传 `--provider`，
不读 `LLM_PROVIDER`）。**若改到 `DASHSCOPE_API_KEY` 那一行，后续全部
跑批会鉴权失败，而排查方向多半会指向平台。**

此外，Copilot 登录框卡住的那几轮里，Agent 对着一个**真实微软账号的
身份验证界面**连按了 12 次回车。

两条都应写入 M5 安全评估：**Agent 在失控重复时会向任意模态框发送输入，
包括身份验证界面；且会访问并修改任务范围外的敏感文件。**
这些是有证据的、可复现的风险，不是假想。

建议：`.env` 移出仓库目录，评测前临时提供或改用系统环境变量。

## 10. 稳定性测试

由 `scripts/stability_run.py` 跑，对应 M2 验收标准 10。**成功率在这里
不是指标**——任务失败无所谓，进程崩溃、资源持续上涨、异常无法归类才是。

| 项 | 结果 |
|---|---|
| 连续运行 | **30.6 分钟 / 22 轮** |
| 进程崩溃 | **否** |
| 异常轮次 | **0/22** |
| 线程 | 12 → 13（+0.03/分钟） |
| 句柄 | 371 → 1520，稳态 **−0.1/分钟** |
| RSS | 72 → 189 MB，峰值 208 MB，稳态 **+0.64 MB/分钟** |

### 10.1 判泄漏要看稳态斜率，不是整段斜率

这一节记录一个方法论错误，因为它差点让我们得出相反的结论。

第一版脚本对整段采样做最小二乘拟合，报出：

    RSS 斜率 +1.69 MB/分钟   **可疑：内存持续上涨**

据此我判断存在句柄泄漏，查出「每轮新建 LLM 后端且从不 close」，
修掉之后重跑 30 分钟。两次数据放在一起才看清：

| | 22.2 分钟 | 30.6 分钟 |
|---|---|---|
| RSS 终值 | 189 MB | **189 MB** |
| 句柄终值 | 1521 | **1520** |

**跑久了 8 分钟，两个终值几乎一模一样。** 真泄漏的话跑更久必然更高——
实际是启动期爬升后收敛到稳态（加载 OCR/UIA/dxcam、线程池与连接池预热）。

**整段拟合把启动期的陡坡摊到全程**，在一条先涨后平的曲线上必然报出
「持续上涨」。更糟的是句柄那一项算出 +9.9/分钟而阈值定在 10.0——
**差 0.1 就翻转结论**。同一次运行，RSS 报「可疑」而句柄报「正常」，
仅仅因为阈值卡的位置不同。

改成分段之后：整段斜率描述「这一跑总共涨了多少」，**后半段斜率回答
「稳态之后还在不在涨」，只有后者能判泄漏**。合成数据验证：饱和曲线
整段 +3.11 而稳态 +0.00，真泄漏两者都是 +5.00。

### 10.2 结论要分开说

- **句柄没有泄漏。** 稳态 −0.1/分钟，1520 是稳态值不是增长中的值。
- **RSS 有真实的缓慢增长。** 稳态 +0.64 MB/分钟，按此速率 4 小时约
  +150MB。对客机 12GB 内存不构成风险，但它是真的，记录在案。
- **那次「修句柄泄漏」的改动仍然是对的**（不关 HTTP 客户端就是资源
  泄漏），但**当时给出的理由是错的**——它不是句柄上涨的原因，
  它泄漏的量被启动期的 1100+ 句柄淹没了。修得对，理由错，分开记。

## 11. 人工错误标注

对 5 条代表性轨迹跑 `python -m cli label`，共标注 16 步。
数据在 `docs/m2-error-labels.json`，对应 M2 验收标准 6。

| 标签 | 次数 | 占比 |
|---|---:|---:|
| `app_state`（界面状态不符预期） | 11 | 69% |
| `premature_done`（过早收工） | 9 | 56% |
| `stuck_loop`（原地打转） | 6 | 38% |
| `planner_bad`（拆解有问题） | 1 | 6% |

标签组合：`app_state + premature_done` 9 次、`stuck_loop` 单独 4 次、
`app_state + stuck_loop` 2 次、`planner_bad` 1 次。

### 11.1 两条独立路径得出同一个结论

**`premature_done` 一次都没有单独出现过**——9 次全部与 `app_state` 同现。

这与 §3.3 的实测（零动作报完成 49% → 0%，只清了桌面）**独立地对上了**：
一条来自成功率统计，一条来自人工逐步标注，**两条路径都指向「过早收工
不是模型的固有毛病，是环境残留触发的」**。

### 11.2 `grounding_off` 零频次

43 条轨迹、185 次点击，**没有一次被标为定位偏差**。这支撑了对模式 B 的
预期判断：grounding 不是当前瓶颈，换本地定位模型的收益在 token 成本
而不在成功率（详见 `docs/m3-执行计划.md` §3.③）。

### 11.3 预设分类里 7 个是零频次

`wrong_action`、`parse_error`、`missing_coords`、`safety_blocked`、
`timeout`、`grounding_off`、`other` 全部为 0。

M4 任务 1 要求「按实测频次重建错误分类体系」——删零频次类、合并近似类、
补新发现类。这张表就是删减依据。同时**要补一类预设里没有的**：
计划与应用实际行为错配（§6 的 F5），目前只能勉强套用 `planner_bad`。

### 11.4 三种子形态挤在同一个标签下

`premature_done` 的 9 次里其实有三种不同机制，靠 note 区分：

| 形态 | 例 |
|---|---|
| 把上一轮残留误读成自己动作的结果 | 「开始菜单已打开，说明点击开始按钮已完成」 |
| 凭空断言屏幕上有不存在的窗口 | 「记事本窗口已在截图中显示」（记事本从未启动） |
| 承认做不到，仍输出 `done` | 「子任务目标未达成」→ `{"done": true}` |

**M4 重建分类时应当把这三种拆开**——它们的检测手段完全不同：
第一种要比对动作前后的帧差，第二种要交叉验证 UIA 窗口列表，
第三种只需约束输出格式。
