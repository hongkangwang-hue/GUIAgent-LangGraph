**端到端 GUI 智能体系统原型 v1.0（第 4 周交付）**

> 执行环境：VMware 虚拟机，Windows 11 中文版，1920×1080，4 vCPU / 12GB
> 规划模型：`qwen3-vl-8b-instruct`（阿里云百炼）
> 撰写日期：2026-09-03　　实测日期：2026-08-23 ~ 08-24

## 一、这一周做了什么

把前三周分头做的三块——屏幕感知、键鼠控制、Agent 框架——接成了一条能跑通的
链路，并用大纲点名的五个桌面任务验证它。

链路是这样走的：

```
用户指令   →  接一句中文自然语言
任务规划   →  拆成若干子任务
屏幕感知   →  截图、DPI 感知、坐标换算
动作执行   →  结构化动作变成真实的鼠标键盘事件
结果反馈   →  程序化判定这一步有没有效果，逐步落盘
```

五个环节各自有独立的模块负责，`core/loop.py` 是把它们串起来的那一层。
每一步都当场写盘，不是跑完再写——这样中途崩溃或人工中断时数据不丢，
后面几周的所有分析都是从这些轨迹里挖出来的。

另外配了一个命令行界面，四个子命令：`run` 执行任务、`replay` 逐帧回放
历史轨迹、`label` 给失败步骤打标签、`config` 查看配置。`run` 默认只演练，
走完整链路但不发出任何键鼠事件，要真正操作桌面必须显式加 `--execute`。

## 二、五个任务测出来的结果

| 任务 | 程序化判定 | 模型自报完成 | 平均步数 | 理论下限 | 平均耗时 |
|---|---|---|---:|---:|---:|
| 打开浏览器 | **5/5** | 5/5 | 6.0 | ~2 | 14.8s |
| 打开指定文件 | **5/5** | 5/5 | 14.8 | ~5 | 35.2s |
| 关闭应用 | **5/5** | 5/5 | 2.0 | 2 | 6.8s |
| 发送消息 | **4/4** | 1/4 | 21.8 | ~4 | 289.1s |
| 搜索指定内容 | **0/5** | 0/5 | 14.0 | ~5 | 44.4s |
| **合计** | **19/24 = 79%** | 16/24 = 67% | | | |

关于分母 24：`发送消息` 只有 4 轮，因为第 2 轮执行到一半时操作者碰了鼠标、
窗口焦点被改动，那一轮在存档里标了 `excluded`，分子分母都不算它。
**标记而不是删掉**——删掉的话没人知道这一批是从 5 轮变成 4 轮的。

主结果由两批运行拼成：前四个任务来自 08-24 00:36 那一轮，`发送消息`
来自 10:05 的补跑。两批的环境配置一致，但 API 延迟差了 8.97 倍，所以
**耗时那一列不能跨批比较**。原始数据都在 `docs/m2-runs/` 下，报告里的
19/24、16/24 都可以自己重算。

### 单步任务和多步任务的分界特别清楚

`关闭应用` 2.0 步、`打开浏览器` 6.0 步，这两个是单步或近单步任务，满分。
一进入多步，步数立刻涨到 14~22，是理论下限的 3~5 倍。

链路本身没问题——感知、坐标换算、动作执行、判定这四层都在正常工作，
185 次点击的坐标全部由模型直接给出，一次定位失败都没有。**瓶颈全在规划层
和反馈闭环上。**

## 三、这份报告最该被记住的不是 79%

同一套代码、同一个模型，我们在一天之内测出过三个成功率：

| 轮次 | 时间 | 成功率 | 零动作报完成 | 这一轮之前改了什么 |
|---|---|---|---|---|
| R3 | 08-24 00:09 | **11/25 = 44%** | 49/101 = 49% | 加了 reset 清场 |
| R4 | 08-24 00:36 | **15/20 = 75%** | 0/65 = **0%** | 关掉记事本会话恢复、任务栏取消固定 Copilot、加 `reset_desktop.py` |
| R5 | 08-24 10:05 | 4/4 = 100% | 3/24 = 13% | 仅补跑 `发送消息` |

**从 44% 到 75%，一行模型相关的代码都没改，改的全是客机环境。**

R3 那 44% 是被四种桌面残留压在那里的：记事本的会话恢复会把上一轮的窗口
拉回前台、系统浮层不属于任何进程所以 `taskkill` 碰不到、模态对话框同理、
还有上一轮没关干净的窗口。把这四样清掉，成功率就上去了。

更说明问题的是「零动作报完成」这一栏：脏环境下 49% 的子任务是一个动作都
没执行成功却报了完成，环境清干净之后直接变成 0%。也就是说，**这个现象
根本不是模型的毛病，是实验设计的毛病。**

还有一次更尴尬的：R1 那一轮 `搜索指定内容` 被判成功，实际命中的窗口标题是
评测脚本自己的控制台窗口——**判定器匹配到了自己**。这个假成功被抓出来之后，
判定规则重写了一遍。

这几件事合起来，是我们后来把「起点检查 + 程序化判据 + 快照名进存档」定成
硬性要求的直接原因。

## 四、程序化判定为什么必须要

一句话：**模型的自我判断和任务的实际状态无关。** 不是偏乐观，是无关。

- 脏环境下它自报完成 20/25，实测只有 11/25——高估
- 干净环境下它自报 16/24，实测 19/24——低估

两个方向都错过。所以这套系统里，一个任务算不算成功，只看程序化判据：
进程在不在运行、窗口标题匹不匹配、文件内容对不对。

配套还有起点检查。每一轮开始前先确认环境处在判据的**反方向**——比如
`打开浏览器` 的判据是「`msedge.exe` 在运行」，那起点必须先确认它没在运行。
不这么做的话，上一轮的残留会让这一轮凭空成功。

## 五、成功率盖住的两件事

### 步数：成功率满分不代表做得好

从落盘轨迹里统计了 43 条轨迹、444 步、174 个子任务：

| 指令 | 平均步数 | 重复步占比 | 成功率 |
|---|---:|---:|---|
| 关闭计算器窗口 | 2.1 | **0%** | 5/5 |
| 打开 Microsoft Edge 浏览器 | 6.0 | **0%** | 5/5 |
| 用记事本打开…测试文档.txt | 13.0 | 9% | 5/5 |
| 在「测试消息」程序里发送… | 14.2 | 30% | 4/4 |
| 打开 Edge，在地址栏搜索… | 15.1 | **75%** | **0/5** |

关系是单调的：**重复率越高、步数越多、成功率越低。** 重复步占七成半的
任务全灭，重复步为零的两个任务满分。

这个指标比成功率更早暴露问题。`发送消息` 4/4 看着完美，但三成的步是白做的；
`打开指定文件` 也是 5/5，平均 13 步而理论下限约 5 步。全部 444 步里有
33% 是在重复上一个动作，最长的一次同一个动作连发了 12 遍。

### 延迟：优化错了地方

按 API 调用 / grounding / 动作执行 / 截图四段拆开：

| 分段 | R4（凌晨 00:36） | R5（上午 10:05） | 变化 |
|---|---:|---:|---:|
| **API 调用** | 1257 ms/步 | **11277 ms/步** | **8.97×** |
| 动作执行 | 378 ms/步 | 473 ms/步 | 1.25× |
| 截图 | 131 ms/步 | 168 ms/步 | 1.28× |
| grounding | 0.00 ms | 0.00 ms | — |
| **单步合计** | **2.75 s** | **13.29 s** | 4.83× |

同一台机器、同一份代码、同一个模型，**只有 API 那一段变了 8.97 倍**，
两批之间唯一的差别是凌晨和上午。

由此有三条结论。第一，优化截图没有收益，它只占单步耗时的 4.8%。第二，
grounding 恒为 0 毫秒，因为坐标是规划模型随动作一起给出的——这个 0 是
后面模式 B 对照实验的基线值。第三也是最要紧的，**云端 API 延迟是评测里
一个不受控的变量**：后面要跑几十次执行做提示词消融，如果版本 1 跑在凌晨、
版本 3 跑在白天，光时段差异就能造出四五倍的「性能差距」。

## 六、五类失败模式

| | 失败模式 | 说明 |
|---|---|---|
| F1 | 环境残留 | 四种形态：会话恢复、系统浮层、模态对话框、上一轮遗留窗口。修完 44% → 75%，**属于实验设计错误** |
| F2 | 零动作报完成 | 由 F1 触发。脏环境 49%，干净环境 0% |
| F3 | 连续重复同一动作 | 占总步数 33%，最长连发 12 次 |
| F4 | 不可观测的子任务导致死循环 | 拆出来的子任务从截图上看不出做没做完，模型就一直试 |
| F5 | 计划与应用实际行为错配 | 拆解粒度和应用的真实交互方式对不上 |

F2 有个值得单独说的形态：模型的 thinking 里明确写着「子任务目标未达成」，
输出的却是 `{"done": true}`——**推理是对的，输出字段错了**。这一点对改进
方向有直接影响：该做的是约束输出格式，不是加强感知。

每一类都有轨迹原文佐证，轨迹 ID 可以用 `python gui-agent.py replay <id> --raw`
复现。

## 七、一次安全事件

实测过程中 Agent 两次访问到仓库里的 `.env`，第二次**修改并保存了它**——
`LLM_PROVIDER` 的值被写成了 `dashscope你好世界测试消息你好世界…`。

机制是这样：记事本的会话恢复把 `.env` 拉回前台 → Agent 误判了焦点 →
「你好世界」这几个字输进去了 → 被保存。

这一轮恰好改到的是不影响评测的字段（执行脚本显式传 `--provider`，不读
`LLM_PROVIDER`）。**但如果改到的是 API Key 那一行，后面所有跑批都会鉴权
失败，而排查方向多半会指向平台，不会指向这里。**

此外，Copilot 登录框卡住的那几轮里，Agent 对着一个**真实微软账号的身份
验证界面连按了 12 次回车**。

这两件事说明：Agent 在失控重复时会向任意模态框发送输入，包括身份验证界面；
并且会访问、修改任务范围之外的敏感文件。这是有证据、可复现的风险，不是假想。
应对措施是把 `.env` 移出仓库目录，评测前临时提供或改用系统环境变量。
`run` 命令默认只演练、必须显式加 `--execute` 才操作桌面，也是因为这件事。

## 八、代码这一层：单元测试

上面都是真机跑出来的结果。代码本身的正确性由单元测试保证，两者互相不能替代。

本周交付的是 `core`（执行闭环）与 `cli`（命令行界面）两个包，2,713 行代码，
配了 8 个测试文件、221 个用例。

```

```

| 测试文件 | 用例数 | 测什么 |
|---|---:|---|
| `test_trajectory.py` | 43 | 轨迹逐步落盘、读回、字段完整性 |
| `test_loop.py` | 35 | Agent Loop 的单步流程与终止条件 |
| `test_retry_escalation.py` | 30 | 重试策略：升级动作而不是重复同一个 |
| `test_cli.py` | 27 | 四个子命令的参数解析与执行路径 |
| `test_allowed_actions.py` | 26 | 动作白名单与提示词的一致性 |
| `test_session.py` | 24 | 会话编排与子任务流转 |
| `test_verify.py` | 22 | 程序化判定的三类判据 |
| `test_run_provenance.py` | 14 | 运行存档记录模板、分辨率、快照等出处 |

用例数最多的三个都集中在执行闭环那一层（轨迹 + 循环 + 重试共 108 条，
占 49%），原因是这一层的失败方式最隐蔽：一步没落盘、一次重试退化成死循环、
一个终止条件写反，都不会抛异常，只会让整轮任务安静地跑偏。

测试不碰真实模型、不碰真实键鼠、不碰真实屏幕——模型调用走脚本化的替身，
键鼠执行走记录式的替身，截图用内存里构造的对象。这样它才能在任何一台机器上
几秒钟跑完，不需要 GPU、网络、API 凭据或桌面环境。

覆盖率分模块：

| 模块 | 覆盖率 | |
|---|---:|---|
| `core/retry.py` | 94% | |
| `core/trajectory.py` | 93% | |
| `core/loop.py` | 89% | |
| `core/verify.py` | 67% | 未覆盖的是三类判据的真实系统调用 |
| `cli/main.py` | 58% | 未覆盖的是需要真实终端的交互路径 |
| `cli/panel.py` | 55% | 同上：rich 的 Live 刷新循环 |

后三个偏低是设计选择而不是遗漏。`verify.py` 未覆盖的部分是真的去枚举进程、

调用那一段由上面那 24 轮实机执行覆盖。`cli` 两个模块未覆盖的是 rich 的实时
刷新循环和执行前的确认提示，这些代码只有在一个真实的、可交互的终端里才会
走到。

`core/reflector.py` 不计入统计——它属于第 6 周的错误检测工作，虽然在 `core`
包里且被 `loop.py` 引用（本周默认关闭），但它的测试不在本交付包内。

## 九、怎么复现

### 跑单元测试

不需要 GPU、网络、API Key 或真实桌面，任何装了 Python 3.10 的机器都行：

```bash
pip install -r requirements.txt          # 装第 1 段即可
python -m pytest                         # 221 passed，约 4 秒
python -m pytest --cov=core --cov=cli --cov-report=term-missing
```

依赖清单第 1 段的边界是实测出来的，不是照着 import 语句猜的：新建一个空
虚拟环境逐步加包，少 `psutil` 会 4 条失败，少 `mss` 会 2 条失败（取不到
屏幕分辨率），补齐才是 221 passed。这两个包乍看像是只有真机才要。

### 跑真机任务

**只能在隔离虚拟机客机内跑。** 本项目的全局约束要求 Agent 的一切键鼠执行
只发生在客机内，宿主机不受控制。

```bash
python tasks/setup_env.py                     # 准备测试目录与文件
python tasks/mock_messenger.py                # 起「测试消息」小程序
python scripts/run_basic_tasks.py --execute --provider dashscope
```

急停有两道：鼠标甩到屏幕左上角触发 PyAutoGUI FAILSAFE，或按全局热键
`Ctrl+Alt+Q`。

`发送消息` 用的是本项目自带的 tkinter 小程序，消息只写本地文件、不联网，
**不接入任何真实通讯软件**。

### 原始数据

`docs/m2-runs/` 下三个文件与本报告一一对应：

| 文件 | 内容 |
|---|---|
| `20260824-000924-all-exec.json` | R3 脏环境全量 25 轮 |
| `20260824-003649-all-exec.json` | R4 清场后全量 25 轮 |
| `20260824-100516-send_message-exec.json` | R5 补跑 5 轮（含 1 轮剔除） |

另有 `m2-behavior-stats.json`（轨迹行为统计）、`m2-error-labels.json`
（人工错误标注）、`m2-stability-report.md` 与 `m2-stability-raw.json`
（连续运行稳定性）。

逐步轨迹与截图只留在客机，没有入库——体积大，而且截图里出现过 `.env` 明文。

## 十、小结

五个基础任务跑通了 19/24，链路本身是通的：感知、坐标换算、动作执行、判定
四层都正常工作，185 次点击没有一次定位失败。问题集中在规划层和反馈闭环。

但比那个 79% 更有价值的是这几条：

- **一个数字不够。** 同一套代码一天之内测出 44% / 75% / 79%，差异全部来自
  评测环境。所以后面每一轮实测都必须记下快照名。
- **模型的自我判断不可用。** 它和实际状态无关，两个方向都错过，判定必须程序化。
- **成功率会盖住问题。** 满分的任务可能用了理论下限 3 倍的步数，重复率是比
  成功率更早的预警信号。
- **优化要挑对地方。** 单步耗时里 API 占八成半，截图只占不到 5%。
- **失控的 Agent 会做危险的事。** 它改过 `.env`，对着真实账号的登录框按过
  12 次回车。这是记录在案的，不是假想。
