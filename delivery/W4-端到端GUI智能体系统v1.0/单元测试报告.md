## 一、概述

第 4 周交付的核心是两个 Python 包——`core`（端到端执行闭环）与 `cli`
（命令行交互界面），合计 2,713 行代码。为验证这两个包的正确性，配套编写了
8 个测试文件、221 个测试用例。

本次执行结果：

> **221 个用例全部通过，无失败、无跳过；两个包的语句覆盖率为 77%。**

测试不依赖 GPU、不依赖网络、不依赖 API 凭据、不依赖真实桌面环境，因此
任何一台安装了 Python 3.10 与 pytest 的机器都可以复现，复现方法见第五节。

为确认交付压缩包本身完整，本次执行**先将交付包解压到一个全新的空目录，
再在该目录中运行**，而非在开发目录中运行——后者无法证明压缩包内容齐全。

## 二、测试范围

### 2.1 纳入统计的两个包

| 包 | 职责 | 对应大纲第 4 周任务 |
|---|---|---|
| `core` | 执行闭环、轨迹记录、程序化判定、重试策略 | 任务 1、2、4 |
| `cli` | 命令行子命令与实时面板 | 任务 3 |

### 2.2 未纳入统计的六个包及其原因

交付包的 `src/` 目录下另有 `agent`、`llm`、`grounding`、`control`、
`perception`、`finetune` 六个包。它们分属第 2、3、5 周的工作，之所以随本包
一并提供，是因为上述两个包在导入时依赖它们——例如 `core/loop.py` 需要
`agent` 的规划器、`control` 的动作执行器与 `perception` 的截图能力，
少任何一个，端到端闭环都无法成立。

这六个包**不计入本报告的覆盖率统计**。它们的测试位于各自所属周次的交付物
中，若在此处一并统计，本周两个包的真实覆盖情况会被稀释。该约定已写入
`pyproject.toml` 的覆盖率配置。

同样被排除的还有 `core/reflector.py`。它属于第 6 周的错误检测与自动重试
工作，虽然位于 `core` 包内、被 `loop.py` 引用（本周默认关闭），但其 17 条
测试在主仓库的 `tests/test_reflector.py`，不在本交付包中。若计入，本周覆盖率
会被它的 66% 拉低，那是误导。

## 三、测试方法

### 3.1 外部依赖的处理方式

单元测试的一条基本要求是：在任何一台机器上都能在数秒内跑完，不能因为缺少
GPU、缺少网络或缺少真实桌面而无法执行。本项目的端到端闭环恰好三样都涉及，
分别按如下方式处理：

**大模型调用。** 通过 `llm/fake.py` 中的 `ScriptedBackend` 替身完成。该替身
按预设脚本返回响应，使测试可以精确构造「模型第 3 步输出了一个越界坐标」
这类场景，而无需真实调用模型。

**键鼠执行。** 通过替身执行器完成，记录「本该发出什么动作」而不真的发出。
这是必要的安全设计——真实的 `ActionExecutor` 会移动鼠标、发送按键，让它在
测试里运行等于让 CI 机器被随机点击。

**屏幕感知。** 用内存中构造的 `Screenshot` 对象代替真实截图。

### 3.2 与真机验证的分工

需要真实桌面或外部服务的能力，由 `scripts/` 与 `tasks/` 下的脚本在虚拟机
客机内承担，不属于本报告范围：

| 脚本 | 验证内容 | 所需条件 |
|---|---|---|
| `scripts/run_basic_tasks.py` | 五个基础任务的端到端成功率 | 虚拟机客机 + 模型 |
| `tasks/setup_env.py` | 任务环境准备 | 虚拟机客机 |
| `tasks/reset_desktop.py` | 每轮之间的环境重置 | 虚拟机客机 |

真机验证的结果见 `基础任务测试报告.md`。

## 四、测试结果

### 4.1 总体

```
221 passed in 3.08s
```

| 指标 | 数值 |
|---|---|
| 测试文件 | 8 个 |
| 测试用例 | **221**（通过 221 / 失败 0 / 跳过 0） |
| 被测语句 | 1,125 条 |
| **语句覆盖率** | **77%** |
| 执行耗时 | 3~5 秒 |

运行测试所需的依赖边界经过实测确认。方法是新建一个空的虚拟环境，逐步安装
并观察结果：

| 安装范围 | 结果 |
|---|---|
| pytest / numpy / pillow / pyyaml / langchain-core / opencv / typer / rich | 4 failed —— 缺 `psutil` |
| 加上 `psutil` | 2 failed —— 缺截图后端，取不到屏幕分辨率 |
| 加上 `mss` | **221 passed, 0 skipped** |

`psutil` 与 `mss` 乍看像是「只有真机才需要」，实际单元测试也需要：
`core/verify.py` 的进程判据依赖 `psutil`，而运行存档要记录屏幕分辨率，
因此需要一个可用的截图后端。`requirements.txt` 已按此结论分段。

### 4.2 用例在四项大纲任务上的分布

| 测试文件 | 用例数 | 对应大纲任务 | 主要验证对象 |
|---|---:|---|---|
| `test_trajectory.py` | 43 | 任务 2 | 轨迹逐步落盘、读回、字段完整性 |
| `test_loop.py` | 35 | 任务 1、2 | Agent Loop 的单步流程与终止条件 |
| `test_retry_escalation.py` | 30 | 任务 2 | 重试策略：升级动作而非重复同一个 |
| `test_cli.py` | 27 | **任务 3** | 四个子命令的参数解析与执行路径 |
| `test_allowed_actions.py` | 26 | 任务 1 | 动作白名单与提示词的一致性 |
| `test_session.py` | 24 | 任务 1、2 | 会话编排与子任务流转 |
| `test_verify.py` | 22 | **任务 4** | 程序化判定：进程 / 窗口 / 文件三类判据 |
| `test_run_provenance.py` | 14 | 任务 4 | 运行存档记录模板、分辨率、快照等出处 |
| **合计** | **221** | | |

四项任务均有测试覆盖。用例数最多的三个文件都集中在「执行闭环」这一层
（轨迹 43 + 循环 35 + 重试 30 = 108 条，占 49%），原因是这一层的失败方式
最隐蔽：一步没落盘、一次重试退化成死循环、一个终止条件写反，都不会抛异常，
只会让整轮任务安静地跑偏。

### 4.3 覆盖率明细

| 模块 | 语句数 | 未覆盖 | 覆盖率 |
|---|---:|---:|---:|
| `core/retry.py` | 52 | 3 | **94%** |
| `core/trajectory.py` | 265 | 18 | **93%** |
| `core/loop.py` | 289 | 33 | **89%** |
| `core/verify.py` | 131 | 43 | 67% |
| `cli/main.py` | 255 | 106 | 58% |
| `cli/panel.py` | 133 | 60 | 55% |
| **合计** | **1,125** | **263** | **77%** |

### 4.4 对三个较低覆盖率模块的说明

**`cli/main.py`（58%）与 `cli/panel.py`（55%）。**
两者未覆盖的部分是需要真实终端的交互路径：rich 的 Live 刷新循环、进度面板
的逐帧重绘、`--execute` 之前的确认提示。这些代码只有在一个真实的、可交互的
终端里才会走到，放进单元测试既跑不起来也没有意义。它们由真机运行覆盖。

**`core/verify.py`（67%）。**
未覆盖的部分是三类判据的真实实现：调用 `psutil` 枚举进程、调用 Windows API
读窗口标题、读取真实文件。测试覆盖的是判据的**组合逻辑与结果解释**（多条
判据如何合成一个结论、失败时如何生成可读的说明），真实的系统调用部分由
`基础任务测试报告.md` 中的 24 轮实机执行覆盖。

这三处的低覆盖率均为设计选择，不是遗漏。

## 五、复现方法

```bash
cd <交付包目录>
pip install -r requirements.txt          # 仅运行测试时，安装第 1 段依赖即可
python -m pytest                         # 预期输出：221 passed
python -m pytest --cov=core --cov=cli --cov-report=term-missing
```

`pyproject.toml` 中已配置 `pythonpath = ["src"]`，**无需安装本包**，在交付
包根目录直接执行即可。

| 操作系统 | Windows 11 |
| Python | 3.10.20（conda 环境 `gui-agent`） |

## 六、结论

第 4 周交付的两个包通过了全部 221 项单元测试，语句覆盖率 77%，四项大纲
任务均有对应的测试覆盖。测试可在无特殊硬件与网络条件的机器上完整复现，
交付压缩包的完整性已通过解压后独立执行验证。

覆盖率较低的三个模块，其原因已在 4.4 节逐一说明，均属于按分工交由真机
运行验证的部分。端到端能力本身的验证结果见 `基础任务测试报告.md`。
